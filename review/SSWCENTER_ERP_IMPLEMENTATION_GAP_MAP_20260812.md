현재 제품에는 직원·수급자·인정·계약·인증·감사의 쓸 수 있는 기반이 있다. 그러나 다음 핵심은 아직 없다.

- 수급자 5개와 직원 6개의 **전체 대상자·완료현황 화면**
- 원천자료에서 계산되는 **자동 업무카드 4개**
- 실제 **전체 수급자–요양보호사 일정**
- 실제 **사회복지사 달력·방문일정·연차·개인일정**
- 공단 계획일정 Excel과 전날 태그 Excel 가져오기
- 태그 시간에 따른 30분 단위 자동보정과 `확인요망`
- 실제 파일함
- 설정의 계정관리·센터정보·센터 한마디·감사로그

반대로 다음 옛 기능은 여전히 코드와 테스트에서 활성 정답처럼 남아 있다.

- 인정전환 preview·최종확인·일괄적용
- 계약에 붙는 W2 급여계획서와 계약·인정기간 저장거부
- 단계·담당자·첨부가 있는 복잡한 업무카드
- 대시보드 `localStorage` 내 할 일
- 직원상담의 상담내용·사유와 건강검진의 유형·결과·면제상태
- 5분 최적화·1,799초·수가행을 포함한 옛 RFID 정정안

- 현재 메뉴들은 그대로 유지한다.

- 사회복지사 메뉴 하나를 달력·방문·마감·연차·개인일정의 업무 허브로 사용하며 외부 앱을 만들지 않는다.
- 파일함·본인부담금·입출력 등 기존 메뉴를 이번 재정렬이라는 이유로 삭제하지 않는다.

최소 폐기:

2. 새 forward migration에서 계획서가 계약·인정기간을 강제하던 정방향 trigger 3개와 역방향 trigger 2개만 제거한다.

5. `erp_backup` read-only와 테이블·기존 행·PK/FK·감사 연결·SELECT는 보존한다.
6. 전후 행 수·PK·전체 행 fingerprint·권한·trigger 목록이 예상과 일치해야 한다.

### 5.3 서비스계약 최소화와 종료처리

- 신규 입력·API·UI는 서비스 종류·시작일·종료일·종료사유만 사용한다.
- 현재 남아 있는 급여개시일·계약서명자 신규 입력과 응답 노출은 제거한다.
- 기존 DB 열과 저장값은 실제 현황을 확인하기 전 물리 삭제하지 않는다.
- 계약 종료는 계약종료일과 선택 종료사유를 저장하는 동작이다.
- 수급자를 `계약종료` 상태로 바꾸는 것은 별도의 수동 동작이다.
- 계약 종료가 수급자 상태를 자동으로 바꾸거나, 상태변경이 계약을 자동종료하면 안 된다.
- 현재 백엔드 종료 API와 수급자 상태 PATCH 기반은 재사용하되, 실제 버튼·상태선택 화면과 두 동작의 분리 테스트를 추가한다.

최소 권한:

- 센터장과 관리책임자는 하나의 `ADMIN`이다.
- USER 계정은 아직 계정에 연결되지 않은 기존 사회복지사·간호사 직원만 선택해 1:1로 연결한다. 계정을 만들면서 직원 레코드를 새로 만들거나 이미 연결된 직원을 중복 연결하지 않는다.

- PIN 재생성 뒤 기존 PIN과 기존 세션은 즉시 무효다.
- 사용중지는 삭제가 아니라 `login_allowed=false`와 세션버전 증가다.

## 10. S5 — 태그 Excel·자동보정·직원교체

현재 관련 모델·parser·API·보정코드는 전부 `MISSING`이다.

### 10.1 최소 보정 규칙

계획 시작 `P`를 기준으로:

| 태그 시작 | 보정 시작 |
|---|---|
| `P-59분` ~ `P-30분` | `P-30분` |
| `P-29분` ~ `P+29분` | `P` |
| `P+30분` ~ `P+59분` | `P+30분` |
| `P-60분` 이하 또는 `P+60분` 이상 | 자동수정 없음, `확인요망` |

- 수급자·요양보호사·날짜와 위 시작범위를 통과한 후보가 정확히 1개일 때만 짝을 맺는다.
- 후보가 0개 또는 2개 이상이면 더 가까운 후보가 있어도 자동선택하지 않는다.
- 한 번의 가져오기에서 한 계획일정과 한 태그행은 각각 최대 한 번만 짝에 사용할 수 있다.
- 서비스시간은 `태그 종료-태그 시작`을 30분 단위로 내린다.
- 서비스시간은 30분 미만이면 자동수정하지 않고 `확인요망`, 480분 초과면 480분으로 제한한다.
- 종료시간은 `보정 시작+확정 서비스시간`이다.
- 시작·종료는 한 transaction에서 함께 바꾸며 한쪽만 바꾸지 않는다.
- 종료태그 없음, 계획만 있음, 태그만 있음, 범위초과, 비정상값, 후보 0/2개 이상은 달력에 세부사유 없이 `확인요망`만 표시한다.
- `계획만 있음`은 Excel이 실제로 포함한 날짜 범위에서만 판정한다.
- `태그만 있음`은 가짜 계획일정을 만들지 않고 해당 날짜의 가져오기 예외로 `확인요망`만 표시한다.

### 10.2 원본과 재가져오기

- 원본 Excel bytes·SHA-256·가져온 시각을 불변 보관한다.
- 파일명이 달라도 콘텐츠 SHA-256이 같으면 같은 원본으로 처리한다.
- 원본행 번호와 가공 전 수급자·요양보호사·날짜·시작·종료를 보관한다.
- 자동수정 전후 일정과 원본행 연결을 보관한다.
- 자동보정도 `SYSTEM/IMPORT` 행위로 전후값·원본·원본행을 감사한다.
- 첫 태그 적용 전에는 사람이 고친 일정도 자동보정할 수 있다.
- 첫 태그 반영 뒤 사람이 다시 자유롭게 수정할 수 있다.
- 날짜별로 한 번 적용된 날짜는 다른 파일로 다시 들어와도 건너뛴다.
- 같은 파일에 처리된 날짜와 새 날짜가 섞이면 새 날짜만 처리한다.
- 일반화 queue·lease·heartbeat·재시도 플랫폼은 만들지 않는다.

### 10.3 직원교체

- `수급자+서비스종류+날짜+시작+종료`가 같은 실제 제공행을 한 묶음으로 만든다. 방문요양과 방문목욕 모두 한 묶음에 서로 다른 제공자 1명 또는 2명이 올 수 있다.
- 개별 태그행을 일렬로 비교하지 않고, 시간순으로 직전 묶음과 현재 묶음의 제공자 집합을 비교한다.
- 수급자·서비스별 실제 급여제공을 날짜·시간순으로 비교한다.
- 첫 제공 묶음은 교체가 아니다.
- 새 제공자마다 1건을 만든다. `A+B → A+C`이면 C만 대상이다.
- 빠진 사람만 있거나 표시순서만 바뀌면 새 대상이 아니다.
- 하루 대체도 교체다. 기존 직원 복귀도 직전 묶음에 없으면 새 교체다.
- Day 1은 새 직원의 첫 실제 제공일이고 기한은 `+13일`이다.
- Day 14 재교체는 미완료 앞 건을 예외종결하고 새 건을 만든다. Day 15 이후에는 적용하지 않는다.
- 실제 제공 원천 정정·무효화 뒤 다시 계산한다.
- 상담일·내용·사유는 저장하지 않고 대상자·완료만 관리한다.

## 16. 완료 판정

이 재정렬 작업은 문서가 그럴듯해졌을 때 끝나지 않는다. 아래가 모두 증명돼야 한다.

1. 활성 정본·matrix에서 옛 정답이 제거됐다.
2. 각 slice가 자기 화면에 필요한 최소 DB·API·UI만 만들었다.
3. 구현 금지 목록이 코드·OpenAPI·DOM·migration·테스트에서 재등장하지 않았다.
4. 권한·날짜 경계·원본보존·감사가 실제 PostgreSQL과 브라우저에서 검증됐다.
5. 결정 대기 항목을 구현자가 임의로 닫지 않았다.
6. 기존 데이터와 사용자 작업물이 보존됐다.

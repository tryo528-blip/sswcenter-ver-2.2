# SSWCenter ERP 최소기능 재분류 기준

> 기준일: 2026-08-12 KST
> 상태: CURRENT DECISION BASELINE
> 목적: 기존 구현을 전부 폐기하지 않고, 최신 사용자 결정에 따라 필요한 기능만 남긴다.
> 주의: 이 문서는 기능 범위를 정리한 문서이며 제품 코드 수정이나 배포 승인을 뜻하지 않는다.

## 1. 프로젝트 한 문장 정의

SSWCenter ERP는 공단 전산을 복제하는 시스템이 아니라, 방문요양기관의 직원·수급자·일정 자료를 바탕으로 놓치기 쉬운 대상자와 업무를 알려주고 완료 여부를 관리하는 내부 운영 시스템이다.

핵심 목적은 다음 세 가지다.

1. 평가 대상자와 완료 여부 관리
2. 수급자와 요양보호사의 계획·실제 일정 관리
3. 사회복지사의 방문·마감·개인 일정 관리

## 2. 과잉설계 금지 원칙

- 실제 업무에 필요한 필드와 동작만 만든다.
- 공단에서 이미 판단·검증하는 내용을 ERP가 다시 검증하지 않는다.
- 대상자 화면은 대상자명과 완료 여부 중심으로 구성한다.
- 발생 이유, 기준일, 기한, 완료자·완료시각, 관련 화면 링크, 일정표 링크를 대상자 완료화면에 추가하지 않는다.
- 화면에서 보이지 않는 DB·API도 불필요하게 일반화하지 않는다.
- 여러 상태가 필요하지 않으면 상태를 늘리지 않는다.
- 체크박스는 프로젝트 전체에서 사용하지 않는다. 단, 보호자를 납부자로 지정하는 기존 선택은 예외로 인정한다.
- 보안, 권한, 변경로그, 원본 보존처럼 사고 방지에 필요한 장치는 유지한다.
- 필요성이 애매한 기능은 미리 만들지 않는다.
- 이 문서의 `DROP`은 앞으로 화면과 업무판정에서 쓰지 않는다는 뜻이다. 기존 DB 행과 이력은 데이터 유무를 확인하고 백업하기 전에는 물리 삭제하지 않는다.

## 3. 메뉴 원칙

기존 사이드바 메뉴는 그대로 유지한다.

1. 대시보드
2. 수급자
3. 직원
4. 사회복지사
5. 본인부담금
6. 입출력
7. 파일함
8. 설정

본인부담금, OCR, 일반 입출력 기능은 이번 재분류의 상세 설계 대상에서 제외한다. 메뉴 삭제를 뜻하지 않는다.

## 4. 기능 재분류표

판정은 기능의 앞으로의 방향을 뜻한다. `MISSING`은 필요한 기능이지만 현재 실제 구현이 없다는 뜻이고, `DEFER`는 형님이 필요성을 확정하기 전에는 구현하지 않는다는 뜻이다.

| 영역 | 판정 | 최소기능 결정 |
|---|---|---|
| PIN 로그인·세션·CSRF·개인정보 보호 | KEEP | 현재 안전장치를 유지한다. |
| 직원·수급자 변경 감사 기반 | KEEP | 여러 사용자가 수정하는 기능의 전후값과 행위자를 기록한다. 일반 화면에는 완료자·완료시각을 표시하지 않는다. |
| 백업·복원 기반 | KEEP | 사용자 화면보다 운영 안전장치로 유지한다. |
| 대시보드 기본 화면 | KEEP | 기존 대시보드를 유지한다. |
| 대시보드 내 할 일 | MOVE TO SOCIAL-WORK HUB | 대시보드에서만 제거한다. 사회복지사 달력 이동 링크는 만들지 않는다. |
| 대시보드 자동 업무카드 | MODIFY | 핵심 기능으로 유지한다. 완료현황 목록과 구분하여 대상자명·업무명·마감일 또는 D-day·완료 처리만 보여준다. 별도 범용 카드 원장을 복제하지 않고 확정된 원천자료에서 계산해 표시한다. |
| 기존 다단계 업무 템플릿 | DROP/DEFER | 여러 단계·첨부·역할별 절차를 강제하는 구조는 제거한다. 인정갱신·계약갱신·계획갱신은 각각 인정만료·계약만료·반기평가 카드에 흡수하고, 나머지 기존 자동카드 종류는 아래 미결정 목록에 둔다. |
| 수급자 기본정보·보호자·연락처 | KEEP | 현재 목록·상세·수정 기반을 유지한다. |
| 보호자를 납부자로 지정 | KEEP | 보호자 선택을 유지하며 이 항목만 체크박스 금지의 예외로 인정한다. |
| 인정번호·인정기간·등급 기록 | KEEP | 내부 참고와 만료 알림의 원천자료로 유지한다. |
| 기존 계획서 통보일 이력 | KEEP/REUSE | 과거 행을 덮어쓰거나 W2 계약연결 테이블과 섞지 않는다. 유효 통보일은 반기평가 완료의 유일한 증거이자 다음 권장기한 계산 원천으로 재사용한다. |
| 수급자 대상자·완료현황 | MISSING | 대시보드의 다섯 이름 `상담반영·반기평가·서류미비·인정만료·계약만료`를 그대로 사용한다. 숫자만 현재 가짜이며, 아래 확정 필터로 대상자와 완료 처리·취소를 새로 만든다. |
| 수급자 수동 상태 | KEEP | `이용중·대기중·계약종료` 상태를 사람이 직접 바꾼다. 계약일로 자동전환하지 않는다. |
| 계약 기록 | MODIFY | 서비스 종류, 계약 시작일, 계약 종료일, 종료사유만 활성 업무필드로 사용한다. 종료사유는 자유문자로 남긴다. |
| 계약 종료 처리 | MODIFY | 계약종료일 입력과 수급자 상태의 `계약종료` 수동전환을 제공한다. 자동전환하지 않는다. |
| 인정전환 일괄기능 | DROP | 기존 인정·등급·계약을 일괄 종료·재생성하는 미리보기·확인·적용 기능을 제거한다. |
| 급여개시일·계약서명자 | DROP | 현재 최소 계약 화면에서 제거한다. |
| 계약 연결형 W2 급여계획서 | DROP | 적용기간 날짜검증·인정/계약 연결·저장거부 구조를 활성 기능으로 사용하지 않는다. 기존 행 유무를 먼저 확인하고, 확인 없이 테이블이나 데이터를 삭제하지 않는다. |
| 반기평가(급여계획) 업무 | MISSING | 마지막 유효 통보일에서 6개월이 되는 달의 말일을 기본 권장기한으로 삼되, 인정만료일·계약만료일 중 먼저 오는 날을 cap으로 적용한다. 완료 처리는 실제 통보일 입력이며 별도 완료 boolean을 만들지 않는다. 계획적용 시작·종료 텍스트는 업무판정에 사용하지 않는다. |
| 직원 기본정보 | MODIFY | 수급자 화면과 같은 목록·상세·수정 구조로 만든다. |
| 직원 재직·퇴직·재입사 | KEEP | 현재 이력 기반을 유지한다. |
| 직원 직종 변경 | MODIFY | 재직 중 직종변경 UI를 만들지 않는다. 직종변경은 퇴사 후 새 직종으로 재입사 처리한다. |
| 직원 자격증·서비스 제공자격 | KEEP | 일정 배정 가능 여부의 기초자료로 유지한다. |
| 직원 교육·상담 완료현황 | MODIFY | 대시보드의 여섯 이름 `보수교육·직원상담·인권교육·연간교육·건강검진·신규교육`을 그대로 사용한다. 대상자명과 완료 상태를 중심으로 단순화한다. |
| 직원 분기상담 내용 | DROP | 상담일·상담내용·미완료사유·면제사유를 새 업무에 사용하지 않는다. 기존 운영자료는 없다는 사용자 결정을 따른다. |
| 직원 건강검진 | MODIFY | 별도 완료 버튼 대신 검진일만 입력한다. 검진일이 있으면 완료로 본다. 검진유형·결과메모·면제사유를 사용하지 않는다. |
| 신규직원 건강검진 주의 | MISSING | 검진일과 입사일의 1년 비교가 현재 없다. 검진일이 입사일보다 정확히 1년을 초과하여 이전이면 주의 표시하고, 검진일이 없으면 미완료로 새로 구현한다. |

| 사회복지사 방문 달력 | MISSING | 사회복지사 허브 안에 월 방문일정, 자동 마감, 연차, 개인 일정을 권한에 맞게 표시하는 실제 달력을 새로 만든다. |
| 사회복지사 연차 | MISSING | 작성자 본인만 등록·수정·삭제하고 센터장은 조회만 가능하며 다른 사회복지사는 볼 수 없게 새로 만든다. |
| 개인 할 일·개인 일정 | MOVE TO SOCIAL-WORK HUB | 작성자만 조회·수정·완료할 수 있다. 센터장도 볼 수 없다. |
| 수급자·요양보호사 계획일정 | MISSING | 실제 일정 원장·API가 현재 없다. 로그인 사용자가 모두 생성·조회·수정·삭제하고 모든 변경을 기록한다. 일시 대체근무는 별도 상태 없이 일정의 요양보호사를 바꾸는 일반 수정이다. 방문요양과 방문목욕은 한 급여에 요양보호사 1명 또는 2명을 허용한다. |
| 공단 계획일정 Excel 가져오기 | MISSING | 로그인 사용자 모두가 공단 Excel로 계획일정을 만들 수 있고, 가져온 뒤에도 일정을 수정할 수 있게 한다. 원본·가져온 계정·처리시각·변경로그를 보존한다. |
| 기존 장기 요양보호사 배정 원장 | DEFER | 계약·재직기간·일반/가족 배정까지 묶인 `CareAssignment`를 계획일정의 필수조건으로 재사용하지 않는다. 기존 자료만 보존하고 별도 필요가 확정될 때까지 화면을 만들지 않는다. |
| 방문요양·방문목욕·일시재가·병원동행·바로돌봄 | KEEP | 다섯 서비스 모두 사용한다. 방문요양과 방문목욕은 1인 또는 2인 급여를 허용한다. |
| 태그 Excel 기반 일정 보정 | MISSING | 로그인 사용자 모두가 전날 태그 원본을 가져올 수 있다. 조건을 통과한 후보가 정확히 하나인 일정만 계획시간 기준 앞 30분·유지·뒤 30분 중 하나로 자동 보정한다. 후보가 둘 이상이면 가까운 것을 추측하지 않는다. |

| 계정관리 | MISSING | 센터장 전용으로 USER 계정 생성, 직원 연결, 닉네임, PIN 생성·재생성, 사용중지를 제공한다. 사용중지는 삭제가 아니라 기존 `login_allowed=false`를 쓰고 기존 세션을 끝내며, 유일한 ADMIN은 사용중지할 수 없다. 기본 ADMIN의 기존 직원 연결은 표시만 하고 임의 재연결 기능을 만들지 않는다. |

| 주소 외부검색·이메일·문자 자동발송 | DEFER | 주소·전화·메모는 텍스트로 저장하되 외부 연동은 만들지 않는다. |
| 계정별 임의 권한 편집기 | DEFER | 권한을 사용자가 마음대로 조합하는 화면을 만들지 않는다. 이 문서의 확정 권한표를 서버에 고정 적용한다. 기존 `account_permission` 행은 데이터 확인 전 삭제하지 않지만 아래 공동기능의 접근판정에는 사용하지 않는다. |
| 직원 임의 업무역할 이력 편집 | DEFER | 기존 자료는 보존하되 일반 업무역할 생성·교체 화면은 만들지 않는다. 직종은 퇴사 후 재입사 원칙을 따른다. |
| 대표보호자·납부자 기간형 이력 UI | DEFER | 현재 보호자와 납부자 선택은 유지하되 복잡한 기간 이력 관리화면은 별도 필요가 확정되기 전에는 만들지 않는다. |
| 옛 공용 일정 팝업 | DROP | 데이터 없는 수급자·요양보호사·사회복지사 공용 팝업은 새 전체 일정과 사회복지사 허브로 교체한다. |

## 5. 계정과 권한

계정 역할은 두 가지로 유지한다.

- `ADMIN`: 센터장
- `USER`: 사회복지사 또는 간호사 직군

센터장과 관리책임자는 같은 사람이며 모든 화면 용어를 `센터장`으로 통일한다. 간호사는 별도 권한체계를 만들지 않고 사회복지사와 동일하게 취급한다.

일반 USER 계정은 설정의 계정관리에서 직원 DB의 사회복지사·간호사 직원을 선택하여 연결한다. 닉네임과 PIN을 설정하고 필요하면 PIN을 다시 생성하거나 계정을 사용중지한다.

현재 최초 설치 과정은 센터장 직원 DB 행과 ADMIN 계정을 함께 만들고 즉시 연결한다. 즉 형님이 말한 ADMIN의 직원 DB 연결은 최초 설치 때 이미 끝난다. 이 연결을 유지하며, 계정관리에서는 연결된 직원을 표시만 한다. 센터장 직원이나 ADMIN 계정을 하나 더 만들거나 임의 재연결하지 않는다.

계정 생성·직원 연결·닉네임 변경·PIN 재생성·사용중지는 감사로그에 남긴다. PIN 원문과 PIN 해시는 감사로그에 남기지 않는다. PIN 재생성·계정 사용중지는 `session_version`을 올려 기존 세션을 끝내고, 별도 계정상태 enum은 만들지 않는다.

| 항목 | 조회 권한 | 수정 권한 |
|---|---|---|
| 전체 수급자·요양보호사 일정 | 로그인 사용자 모두 | 로그인 사용자 모두, 변경로그 기록 |
| 공단 계획일정·태그 Excel 가져오기 | 로그인 사용자 모두 | 로그인 사용자 모두, 원본·실행자·변경로그 기록 |
| 수급자·직원 명단 및 완료현황 | 로그인 사용자 모두 | 로그인 사용자 모두, 변경로그 기록 |
| 사회복지사 방문일정 | 사회복지사를 선택하여 로그인 사용자 모두 조회 | 해당 사회복지사와 센터장 |
| 사회복지사 담당 수급자 연결 | 로그인 사용자 모두 | 로그인 사용자 모두, 변경로그 기록 |
| 사회복지사 연차 | 작성자 본인과 센터장 | 작성자 본인만 |
| 개인 할 일·개인 일정 | 작성자 본인만 | 작성자 본인만 |
| 일반 파일함의 폴더·파일 | 로그인 사용자 모두 | 로그인 사용자 모두, 변경로그 기록 |
| 센터 기본정보·센터 한마디 | 로그인 사용자 모두 | 센터장만 |
| 감사·시스템·가져오기 로그 | 센터장, 설정의 로그 화면 | 사용자 파일함에서 수정하지 않음 |

위 공동기능 API는 로그인 여부와 위 고정 역할만 검사하고 `account_permission` 부여행을 요구하지 않는다. 개인 할 일·개인 일정은 센터장용 감사로그에 사건이나 내용을 남기지 않으며, 소유자는 요청값이 아니라 로그인 계정으로 서버가 정한다.

## 6. 대상자·완료 화면 공통 원칙

- 분류를 선택하면 해당 대상자만 표시한다.
- 행의 핵심 표시는 대상자명과 완료 상태다.
- 체크박스를 사용하지 않는다.
- 미완료 행에는 `완료 처리` 버튼을 표시한다.
- 완료 행에는 `완료` 상태와 `완료 취소` 버튼을 표시한다.
- 완료 변경은 감사로그에 남긴다.
- 발생 이유, 기준일, 기한, 완료자·완료시각, 상세화면 이동, 일정표 연결을 표시하지 않는다.
- 건강검진만 예외로 별도 완료 버튼을 두지 않는다. 검진일을 입력하면 완료, 비우면 미완료로 본다.
- 반기평가도 중복 완료 버튼을 두지 않는다. `통보일 입력`으로 완료하고 잘못 입력한 통보일은 행을 삭제하지 않고 무효화한다.
- 신규직원은 검진일이 입사일보다 1년을 초과하여 이전이면 행에 주의 표시만 한다.

### 6.1 수급자 다섯 업무분류

대시보드에 이미 있는 이름은 정식 이름으로 유지한다. 현재 `1nn/1mm`처럼 보이는 숫자만 고정 예시값이다.

| 분류 | 대상자 필터 | 완료 단위 |
|---|---|---|
| 상담반영 | 선택한 연도에 연 1회. 그 연도 중간에 계약종료 처리된 수급자는 제외한다. | 수급자·연도별 1건, 버튼으로 완료·취소 |
| 반기평가 | 급여계획을 다시 작성할 차례인 수급자. 유효 통보 이력이 없으면 우선 미완료 대상이다. 이력이 생기면 기본 권장기한은 `마지막 유효 통보일 + 6개월이 속한 달의 말일`이고, 해당 계약 종료일 또는 인정 종료일이 더 빠르면 그 빠른 날로 당긴다. | 실제 통보일 입력이 완료. 별도 완료값 없음 |
| 서류미비 | 선택한 월에 수급자–요양보호사 서비스 일정이 하나라도 있는 모든 수급자. 즉 `수급자 × 일정이 있는 월`마다 1건이다. | 수급자·월별 1건, 버튼으로 완료·취소 |
| 인정만료 | 무효·대체되지 않은 적용 인정의 종료일이 `D-100` 알림구간에 들어온 수급자. | 인정 회차별 1건, 버튼으로 완료·취소 |
| 계약만료 | 무효·대체되지 않은 적용 계약의 종료일이 `D-45` 알림구간에 들어온 수급자. | 계약 회차별 1건, 버튼으로 완료·취소 |

서류미비 완료원장은 사람·완료 단계에서 준비하되 대상자 계산은 수급자–요양보호사
서비스 일정 원장과 수동 CRUD가 생긴 뒤 연결한다. 사회복지사 달력자료로 대신하지
않으며 실제 Excel parser 표본은 이 연결의 선행조건이 아니다.

반기평가의 cap은 `언제까지 다시 작성할지`를 정하는 잊음 방지 기준이다. 공단 계획서에 적힌 계획적용 시작일·종료일 텍스트가 계약·인정기간 안에 있는지를 검사하거나 저장을 막는 규칙은 아니다.

업무상 계획적용기간은 계획 시작일부터 다음 반기 말일까지 적고, 그 전에 인정이나 계약이 끝나면 그 만료일까지 적는 것이 원칙이다. 다만 공단 전산에서 이미 작성·검증되는 내용이므로 ERP에서는 이 값을 계산 필드로 만들지 않고, 필요하면 원문 텍스트를 그대로 보관할 뿐이다.

유효 통보일이 전혀 없으면 날짜를 지어내지 않고 반기평가를 `미완료`로 보여준다. 형님이 과거 통보일을 입력하면 그 입력 자체로 해당 회차를 완료하고, 가장 최근 유효 통보일을 기준으로 다음 권장기한과 D-45를 다시 계산한다. 별도 `반기평가 완료` boolean이나 중복 업무행을 만들지 않는다.

### 6.2 직원 여섯 업무분류

이름은 대시보드의 정식 이름을 그대로 사용한다. 현재 2.2 정본의 보수교육 규칙, 삭제된 구 1.0 저장소의 정본 읽기 기록, 현재 노션의 교육·상담·검진 대상 뷰를 서로 대조하여 항목별 경계를 회수했다. 서로 다를 때는 형님의 최신 결정과 구 정본의 명시된 경계를 우선한다.

| 분류 | 회수된 대상·기간 조건 | 완료 판단 |
|---|---|---|
| 보수교육 | 현재 재직 중인 요양보호사. 대상연도와 출생연도의 홀짝이 같고, `대상연도 - 최초 요양보호사 자격연도 > 2`일 때 대상이다. | 해당 연도의 보수교육 완료값 |
| 직원상담 | 선택한 분기의 첫날부터 마지막 날까지 계속 재직한 **요양보호사**. 분기 첫날 입사자와 분기 마지막 날 퇴사자는 포함하고, 분기 중간 입사·분기 말일 전 퇴사자는 제외한다. 화면을 처음 열 때는 현재 분기를 기본으로 보여준다. | 요양보호사·달력연도·분기별 완료 버튼 |
| 인권교육 | 선택한 반기 말일에 재직 중인 직원. 반기 중간 입사자도 말일까지 재직하면 포함하고, 반기 말일 전에 퇴사하면 제외한다. 반기 말일 퇴사자는 포함한다. 같은 반기 안의 재입사는 기존 완료를 이어 쓴다. | 직원·`YYYY-H1/H2`별 완료 버튼 |
| 연간교육 | 선택한 해 12월 31일에 재직 중인 직원. 그해 중간 입사자도 12월 31일까지 재직하면 포함하고, 그 전에 퇴사하면 제외한다. 12월 31일 퇴사자는 포함한다. 장애인학대·노인학대·성희롱·직장내괴롭힘·개인정보보호 5과목을 관리하고 같은 연도 재입사는 완료를 이어 쓴다. | 다섯 과목이 모두 끝나야 직원의 연간교육 완료 |
| 건강검진 | 선택한 해의 신규입사자는 그해 중간에 퇴사해도 대상이다. 그보다 전에 입사한 기존 직원은 그해 12월 31일에 재직 중이어야 하며 12월 31일 퇴사자는 포함한다. 검진일 하나만 관리하고, 신규직원은 검진일이 입사일보다 1 calendar year를 초과하여 이전이면 주의한다. | 검진일이 있으면 완료, 없으면 미완료 |
| 신규교육 | 신규입사·재입사 때마다 새 재직기간에 1건을 만든다. 이후 퇴사해도 그 재직기간의 대상·완료 이력을 지우지 않고, 이전 재직의 완료를 재사용하지 않는다. | 해당 재직기간의 완료 버튼 |

직원 여섯 업무를 하나의 `현재 재직자` 필터로 묶지 않는다. 기간의 시작일과 종료일은 모두 포함한다. 직원상담은 분기 전체 재직한 요양보호사, 인권교육은 반기 말일 재직자, 연간교육은 12월 31일 재직자, 건강검진은 당해 신규입사자와 12월 31일 재직한 기존 직원, 신규교육은 각 재직 시작 건을 대상으로 한다.

근거는 삭제된 구 저장소의 `b00f37d` snapshot에 있던 정본 `docs/02_설계도_구조_기능현황.md` §5.1~5.2와 `35f7e35` snapshot의 업무규칙 추출본을 보존한 읽기 기록이다. 현재 노션의 [교육확인](https://app.notion.com/p/38870766b42f81459256c3a899516aed), [직원상담](https://app.notion.com/p/38870766b42f8179b4b7e66a7ede25fc), [건강검진](https://app.notion.com/p/38870766b42f81ef840cc6ea878b63fe) 대상 뷰도 대조했다. 노인인권·연간교육은 구 규칙과 맞았지만, 노션 직원상담 뷰는 분기 첫날 입사자를 누락했고 건강검진 뷰는 그해 입사 후 중도퇴사자를 누락했다. 따라서 이 두 노션 필터를 새 구현에 그대로 복사하지 않는다. 개인 이름·식별값도 이 문서에 옮기지 않았다.

### 자동 업무카드의 최소 생성 규칙

대상자·완료현황 목록과 자동 업무카드는 다른 화면요소다. 완료현황 목록에는 대상자명과 완료 여부만 표시한다. 자동 업무카드는 잊지 않게 알리는 용도이므로 `대상자명·업무명·마감일 또는 D-day·완료 처리`만 표시한다. 발생이유·담당자·단계·첨부·복수 상태·완료자·완료시각·관련화면 링크는 카드에도 추가하지 않는다.

카드 전용 범용 원장이나 작업큐를 만들지 않는다. 다음 네 종류만 각 원천자료와 완료자료에서 계산하여 대시보드와 달력에 투영한다.

1. 계약만료 — 계약 종료일
2. 인정만료 — 인정 종료일
3. 반기평가 — 가장 최근 유효 통보일과 인정·계약 cap
4. 직원교체 상담 — 실제 급여제공 순서

- 계약만료는 계약 종료일 `D-45`에 알린다.
- 인정만료는 인정 종료일 `D-100`에 알린다.
- 반기평가의 기본 권장기한은 마지막 통보일에서 6개월이 되는 달의 말일이다.
- 해당 인정만료일이나 계약만료일이 기본 권장기한보다 빠르면 반기평가 권장기한도 그 빠른 날로 당긴다. 계산은 `min(6개월 월말, 인정만료일, 계약만료일)`이다.
- 반기평가는 이렇게 확정한 실제 권장기한 `D-45`에 미리 알린다.
- 마지막 통보일이 없으면 계산용 임의 날짜를 만들지 않고 즉시 미완료 대상으로 보여준다. 과거 통보일 입력 뒤 최신 통보일로 다시 계산한다.
- 위 날짜는 카드를 만들어 안 잊게 하는 내부 기준일 뿐이다. 급여계획서에 적힌 적용 시작·종료 텍스트를 검증하거나 저장을 막는 데 사용하지 않는다.
- 카드가 완료되면 달력의 같은 마감도 완료로 표시한다.
- 카드는 알림 시작일에 나타나며 기한이 지나도 미완료이면 사라지지 않는다. 완료하면 활성 카드에서 빠지되 완료 이력과 달력의 완료 표시는 보존한다.
- 유효 통보일이 없는 반기평가는 계산할 마감일이 없으므로 미완료 목록·카드에는 보이지만 달력에는 임의 날짜로 표시하지 않는다.

현재 정적 템플릿의 `인정서갱신·계약갱신·계획갱신`은 각각 위 `인정만료·계약만료·반기평가`에 흡수한다. `신규수급자·신규직원입사자료준비/신규직원업무·퇴사직원업무·수급자종료` 자동카드는 형님이 유지 여부를 결정하기 전까지 새로 구현하거나 조용히 되살리지 않는다.

## 7. 사회복지사 달력 최소 동작

- 기본은 한 달 보기다.
- 달력은 작은 카드 안에 가두지 않고 사회복지사 화면의 남는 가로·세로 작업영역을 채운다.
- 사회복지사를 선택하면 담당 수급자 목록과 방문일정을 표시한다.
- 담당 수급자 연결 자체는 로그인 사용자 모두가 누구의 것이든 생성·변경·삭제할 수 있고 모든 변경을 기록한다.
- 선택한 사회복지사가 담당 수급자마다 달력월 1건의 방문일정을 입력·수정·삭제할 수 있고, 센터장도 같은 작업을 할 수 있다. 같은 사회복지사·수급자·달력월의 두 번째 방문일정은 만들지 않는다.
- 월간 날짜 칸을 선택하면 선택한 주를 중심으로 전주·선택한 주·다음 주의 3주 보기를 표시한다.
- 3주 보기에서 달력 영역을 우클릭하면 한 달 보기로 돌아간다.
- 확대·복귀해도 선택한 사회복지사와 보고 있던 달을 유지한다.
- 방문일정에는 수급자명과 시간만 간결하게 표시한다.
- 방문일정에서 수급자 상세화면으로 이동하는 링크는 만들지 않는다.
- 자동 마감은 업무카드의 실제 기한 날짜에 표시한다. 달력에서 직접 완료·완료취소하지 않고 같은 업무카드의 완료값을 읽어 표시한다.
- 개인 일정은 작성자 외에는 서버 응답에서도 제외한다.

### 7.1 전체 수급자·요양보호사 일정의 최소 수정

- 로그인 사용자 모두가 일정의 수급자·서비스·요양보호사·날짜·시작·종료를 생성·수정·삭제할 수 있고 모든 전후값을 기록한다.
- 일시 대체근무는 별도 테이블·상태를 만들지 않고 해당 일정의 요양보호사를 대체자로 바꾸는 일반 수정으로 처리한다.
- 계획일정에서 요양보호사를 바꾼 사실만으로 직원교체 상담을 만들지 않는다. 태그로 확인된 실제 제공순서가 바뀌었을 때만 만든다.
- 방문요양·방문목욕의 같은 수급자·서비스·날짜·시작·종료 묶음에는 서로 다른 요양보호사 1명 또는 2명만 둔다.
- 계약·인정·기존 `CareAssignment`를 일정 저장의 필수 FK나 저장차단 조건으로 사용하지 않는다.
- 동일 요양보호사의 다른 일정 겹침, 동일 수급자의 서로 다른 일정 겹침, 근무일의 재직·서비스자격 불일치를 경고할지 저장을 막을지는 아래 중요 미결정으로 남긴다. 같은 수급자·서비스·날짜·시작·종료로 묶인 정상 2인 급여는 충돌이 아니다. 결정 전에는 옛 hard gate도, 무검사도 정답으로 구현하지 않는다.

## 8. 직원교체 상담 자동대상 최소 계약

2.1 GitHub 정본에서 다음 규칙을 회수해 유지한다.

1. 배정표를 바꿨다는 사실만으로 대상자를 만들지 않는다.
2. 수급자·서비스별 `실제 급여제공`을 날짜와 시간 순으로 놓고 직전 제공자와 새 제공자를 비교한다.
3. 서비스 사이에 빈 날이 있어도 가장 최근 실제 제공자를 직전 제공자로 본다.
4. 새 요양보호사가 처음 실제 급여를 제공한 날이 Day 1이고, 상담 완료기한은 그날을 포함한 14일째, 즉 `첫 제공일 + 13일`이다.
5. 하루만 대신 근무한 경우도 똑같이 직원교체로 본다. `일시대체` 같은 별도 상태는 만들지 않는다.
6. Day 14에 다시 직원이 바뀌면 완료되지 않은 앞 케이스를 예외 종결하고 새 케이스를 만든다. Day 15 이후의 재교체에는 이 예외를 적용하지 않는다.
7. 실제근무가 정정되거나 무효화되면 대상 여부와 기준일을 다시 계산한다.
8. 상담내용·상담일·사유를 저장하지 않고 대상자와 완료 여부만 관리한다.

방문요양과 방문목욕은 한 급여에 서로 다른 요양보호사 1명 또는 2명이 올 수 있다. 2인 급여는 같은 수급자·서비스·날짜·시작·종료의 실제 제공행을 한 묶음으로 보고, 시간순으로 직전 묶음과 현재 묶음의 요양보호사 집합을 비교한다.

- `현재 묶음 - 직전 묶음`에 새로 들어온 사람마다 직원교체 1건을 만든다.
- `A+B → A+C`이면 C만 직원교체 대상이다.
- 빠져나간 사람만 있거나 같은 두 사람의 표시 순서만 달라졌다면 새 직원교체를 만들지 않는다.
- 첫 실제 제공 묶음은 비교할 직전 제공자가 없으므로 직원교체를 만들지 않는다.
- 하루 대체 뒤 기존 직원이 돌아오면, 돌아온 직원도 직전 묶음에 없던 사람인 경우 새 교체로 판정한다. Day 14 재교체 예외는 그대로 적용한다.

## 9. 태그 Excel 일정 보정 최소 계약

하나의 계획일정은 다음 정보로 구성한다.

- 수급자
- 요양보호사
- 날짜
- 시작시간
- 종료시간

처리 순서는 다음과 같다. 아래 조건을 모두 통과한 한 쌍만 `명확히 짝이 맞는 일정`이다. 계획 시작시간은 이미 30분 단위라고 전제한다.

1. 가능한 매일 전날 요양보호사 태그 Excel을 가져온다.
2. 수급자·요양보호사·날짜가 같은 계획일정 후보만 찾는다.
3. 각 후보의 계획 시작시간 `P`와 태그 원본 시작시간의 차이를 분 단위로 비교한다.
4. 태그 시작이 `P-59분`부터 `P-30분`이면 보정 시작은 `P-30분`이다.
5. 태그 시작이 `P-29분`부터 `P+29분`이면 보정 시작은 `P`로 유지한다.
6. 태그 시작이 `P+30분`부터 `P+59분`이면 보정 시작은 `P+30분`이다.
7. 태그 시작이 `P-60분` 이하 또는 `P+60분` 이상이면 그 후보와 자동으로 짝을 맺지 않는다.
8. 예를 들어 계획 시작이 `09:00`이면 `08:01~08:30 → 08:30`, `08:31~09:29 → 09:00`, `09:30~09:59 → 09:30`이다. `08:00`과 `10:00`은 자동보정하지 않는다.
9. 종료시간은 태그 종료를 계획 종료에 독립적으로 맞추지 않는다. `태그 종료 - 태그 시작`으로 원본 서비스시간을 구하고, 확정된 서비스시간을 보정 시작에 더해 보정 종료를 만든다.
10. 서비스시간은 30분 단위로 내린다. `30~59분 → 30분`, `60~89분 → 60분`, `180~209분 → 180분`, `210~239분 → 210분`이며 나머지도 같은 규칙이다.
11. 인정하는 최소 서비스시간은 30분, 최대 서비스시간은 480분이다. 원본 서비스시간이 30분 미만이면 자동수정하지 않고, 480분을 넘으면 서비스시간은 480분까지만 인정한다.
12. 계산식은 `min(480, floor(원본 서비스분 / 30) × 30)`이며 원본 서비스분이 30 이상일 때만 적용한다.
13. 따라서 원본 서비스시간이 185분이고 보정 시작이 `09:00`이면 서비스시간은 180분, 보정 종료는 `12:00`이다.
14. 수급자·요양보호사·날짜와 시작시간 범위를 통과한 후보가 정확히 하나일 때만 그 일정과 짝을 맺는다.
15. 후보가 없거나 둘 이상이면, 하나가 더 가까워 보여도 추측하여 자동선택하지 않는다.
16. 한 계획일정과 한 태그행은 가져오기 한 번에서 각각 한 번만 짝을 맺을 수 있다.
17. 보정 시작과 서비스시간 구간이 모두 확정될 때만 시작·종료를 한 번에 수정한다. 하나라도 실패하면 시작·종료를 모두 수정하지 않는다.
18. 종료 태그 없음, 계획만 있음, 태그만 있음, 시작범위 초과, 30분 미만 서비스, 비정상값, 후보 0개·2개 이상은 모두 일정을 수정하지 않는다.
19. `계획만 있음`은 Excel 안에 실제로 포함된 날짜 범위에 대해서만 판정한다.
20. 달력에는 세부 원인을 표시하지 않고 `확인요망` 하나로만 표시한다. 태그만 있는 경우에도 가짜 계획일정을 만들지 않고 해당 날짜의 가져오기 예외표시로 `확인요망`만 보여준다.

원본과 변경이력은 다음 방식으로만 보존한다.

- 가져온 원본 Excel 파일은 바이트 그대로 변경 불가 보관한다. 콘텐츠 해시와 가져온 시각을 함께 기록한다.
- 원본에서 읽은 각 태그행은 원본 행번호, 수급자, 요양보호사, 날짜, 가공 전 시작·종료값을 원본 연결과 함께 보관한다.
- 자동수정 이력에는 계획일정 ID, 수정 전 시작·종료, 수정 후 시작·종료, 원인이 된 원본과 태그행을 기록한다.
- 현재 계획시간은 바뀌어도 위 수정 전 값과 원본 태그값은 덮어쓰지 않는다.
- 아직 그 날짜의 태그가 적용되지 않았다면 첫 정상 태그 가져오기가 사람이 고친 계획일정도 자동수정할 수 있다. 첫 태그 반영 뒤에는 사람이 다시 자유롭게 고칠 수 있다. 모든 전후값을 감사로그에 남긴다.

파일명이 달라도 콘텐츠 해시가 같으면 같은 원본으로 본다. 또한 날짜별로 한 번 적용이 끝난 날짜는 이후 수정된 Excel에 같은 날짜가 다시 들어와도 적용을 건너뛴다. 한 파일에 이미 적용된 날짜와 새 날짜가 섞여 있으면 새 날짜만 처리한다. 원본은 보관하되 중복 날짜의 일정은 다시 수정하지 않는다. 자동수정도 시스템 행위로 변경로그에 남긴다.

쉽게 말하면 원본 Excel은 `원본 사진`, 자동수정 이력은 `수정 영수증`처럼 따로 남긴다. 일반화된 자료처리 플랫폼은 만들지 않는다.

## 10. 형님이 물은 기존 기능의 정체

### 인정전환과 인정전환 최종확인

옛 인정전환은 새 인정기간이 시작될 때 기존 인정기간·등급·장기요양 계약을 전날로 한꺼번에 끝내고, 새 인정·등급·대체계약을 한 번에 만드는 기능이다. `최종확인`은 별도 업무자료가 아니라 이 대량 변경을 실행하기 직전 누르는 안전 확인 체크박스였다.

최신 결정에서는 공단이 이미 인정과 계약의 적합성을 검증하고, ERP에서는 사람이 필요한 기록만 관리하면 된다. 따라서 이 일괄 전환과 최종확인은 제거하고 인정번호·인정기간·등급은 사람이 직접 기록한다.

### 급여개시일·계약서명자·종료사유

옛 설계에서 급여개시일은 실제 서비스가 시작된 참고 날짜였고, 계약서명자 이름·관계·전화는 계약 당시 서명한 사람을 복사해 둔 메모였으며, 종료사유는 계약을 끝낸 이유를 적는 자유문자였다. 최신 결정으로 급여개시일과 계약서명자는 제거하고, 종료사유 자유문자는 계약에 남긴다.

### 계약 연결형 W2 급여계획서

옛 W2 기능은 급여계획서를 특정 계약에 붙이고, 계획 적용기간이 계약기간·인정기간 안에 들어오는지 ERP가 다시 검사하여 맞지 않으면 저장을 막으려던 구조다. 공단 전산이 이미 그 검증을 하고 계획 적용기간은 ERP에서 판단할 날짜가 아니라는 최신 결정과 맞지 않는다. 따라서 이 테이블과 검증은 새 기능으로 이어가지 않는다. 반기평가는 기존 통보일 원장을 완료 증거로 재사용하고 별도 완료 원장을 복제하지 않는다.

### 안전 폐기 방식

- 인정전환 화면·호출 API·OpenAPI 경로는 제거하되 이미 기록된 인정·등급·계약·감사행은 보존한다.
- 적용된 migration 파일을 고쳐 과거 이력을 바꾸지 않는다. 새 forward migration으로
  W2 전용 정방향 trigger 3개·역방향 trigger 2개만 제거하고 대응 function과 일반
  무결성 trigger/function은 보존한다. 앱 table 쓰기권한과 identity sequence
  USAGE/UPDATE를 회수해 table SELECT만 남기고 `erp_backup` read-only를 유지한다.
- `recipient_service_plan_notice` 테이블과 기존 행은 읽기 전용 역사자료로 보존한다. 물리삭제하지 않는다.
- 기존 `recipient_plan_notification`은 반기평가의 활성 계산 원천이므로 폐기하지 않는다.
- 옛 W2·WorkCadence 계획과 테스트 매트릭스는 본문을 고치지 않고 `RETIRED — 역사 증거 전용`으로 표시하여 새 작업지시로 사용하지 못하게 한다.

### 파일함 삭제의 최소 안전선

- 일반 파일 삭제는 지정된 파일함 루트 안에서 휴지통으로 이동하는 동작이다. 로그인 사용자 모두 복원할 수 있다.
- 영구 물리삭제는 1차 범위에서 만들지 않는다.
- 일반 파일함의 삭제가 import 원본·감사·시스템 로그를 연쇄 삭제해서는 안 된다.
- 사용자가 임의 서버 경로를 입력하거나 파일함 루트 밖으로 이동할 수 없게 한다.

## 11. 기존 정본·테스트 처리 원칙

다음 기존 설계는 최신 결정의 근거로 사용하지 않는다.

- 계약 연결형 W2 급여계획서의 계획적용기간 hard reject·역방향 trigger. 단 반기평가 권장기한의 인정만료·계약만료 cap은 잊음 방지 규칙으로 유지한다.
- 인정전환의 preview·hash·일괄 종료·재생성
- 상담내용·사유를 필수로 요구하는 직원 분기상담
- 네 가지 이상 공식 업무상태와 단계형 완료
- 체크박스를 강제하는 교육·전환 UI 테스트
- 사회복지사와 간호사를 별도 탭·별도 권한으로 나누는 설계
- 외부 WorkCadence 연동 계획
- 대시보드의 가짜 숫자와 정적 다단계 업무 템플릿. 다섯·여섯 업무 이름은 정식 이름으로 유지한다.
- 기존 `CareAssignment`를 새 계획일정의 필수 계약으로 삼는 설계
- 공동 일정·명단·완료·담당연결에 기존 `account_permission` 부여를 요구하는 gate

기존 테스트가 위 동작을 강제하면 제품을 옛 테스트에 맞추지 않고 테스트와 정본을 최신 결정에 맞게 다시 작성한다.

- 현재 로그인 계정의 직원 연결정보 제공

- 설정의 계정관리·감사로그·센터정보·센터 한마디

## 14. 남은 결정·입력 — 확정 전 해당 부분 구현 금지

대부분의 세부규칙은 확정됐다. 아래 두 가지는 형님이 결정해야 하고, 두 가지는 실제 입력·사례가 있어야 닫을 수 있다.

### 형님 결정 2개

1. 일정 저장 때 동일 요양보호사의 다른 일정 겹침, 동일 수급자의 서로 다른 일정 겹침, 근무일의 재직·서비스자격 불일치를 `주의표시 후 저장 허용`으로 할지 `저장차단`으로 할지. 정상 2인 급여는 충돌에서 제외하고 계약·인정·기존 장기배정은 어느 쪽이든 필수검사에서 제외한다.
2. 기존 자동카드 가운데 새 최소업무로 아직 흡수되지 않은 `신규수급자·신규직원·퇴사직원·수급자종료` 네 종류를 각각 유지할지 보류할지.

### 실제 입력·사례 2개

1. 실제 공단 계획일정·태그 Excel의 시트명·열 이름·수급자·직원 식별값 표본
2. 기존 ADMIN의 직원 연결이 실제로 잘못된 사례가 생긴 경우에만 적용할 재연결 절차

Excel 표본이 나오기 전에는 이름만으로 수급자·직원을 짐작해 연결하는 파서를 만들지 않는다. 위 결정 전에는 경고·차단이나 옛 자동카드의 생존을 구현자가 임의로 정하지 않는다. 그 밖에는 필요하다는 이유만으로 상태·필드·화면·연동을 추가하지 않는다.

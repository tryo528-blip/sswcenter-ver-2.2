## 0. 최상위 원칙

SSWCenter ERP는 공단 전산을 복제하지 않는다. DB는 평가 대상·완료, 수급자–요양보호사 일정, 사회복지사 업무흐름을 놓치지 않게 하는 최소 자료만 활성 계약으로 둔다.

- 적용된 migration은 수정·재사용·운영 downgrade하지 않는다. 변경은 현재 head 뒤의 새 forward migration으로만 한다.
- `DROP`·`RETIRE`는 활성 API·화면·업무판정에서 제거한다는 뜻이다. 기존 table·column·row·PK/FK·감사 연결은 현황 확인과 백업 전 물리삭제하지 않는다.
- 각 S1~S6 slice는 자기 화면에 필요한 table·column·FK만 만든다. 다음 slice의 nullable FK·상태·queue를 미리 만들지 않는다.
- 수정 가능한 aggregate는 양의 `row_version`과 낙관적 잠금을 유지한다.
- 공동업무 변경은 같은 transaction에서 행위자·시각·전후값을 `audit_event`에 남긴다.
- 주민등록번호·PIN 비밀값은 audit JSON에 넣지 않고 기존 암호화·reveal·정정 보안을 유지한다.
- 사용자 삭제가 원본·감사·역사자료를 cascade 삭제해서는 안 된다.
- UI checkbox 금지와 DB boolean은 구분한다. 버튼형 완료에는 내부 boolean을 쓸 수 있지만 반기평가는 예외다.

## 2. R0 안전폐기

### 2.1 인정전환

preview hash, 최종확인, 일괄 apply route와 service 호출을 제거한다. 인정번호·인정기간·등급과 계약은 각각 일반 등록·수정·종료로 관리한다. 이를 위해 새 전환상태나 이력 table을 만들지 않으며 기존 업무행을 변경·삭제하지 않는다.

### 2.2 `20260809_0018_w2_service_plan_notice.py`

적용된 `0018`과 downgrade는 건드리지 않는다. 새 forward migration에서 다음 W2 전용 trigger 다섯 개만 제거한다. 대응 function은 이번 R0에서 삭제하지 않는다.

- `ct_service_plan_notice_before_contract_start`
- `ct_service_plan_notice_within_contract`
- `ct_service_plan_notice_within_certification`
- `ct_recipient_contract_service_plan_reverse_guard`
- `ct_recipient_certification_period_service_plan_reverse_guard`

다음 일반 무결성 trigger와 대응 function은 유지한다.

- `ct_recipient_contract_recipient_id_immutable`
- `ct_recipient_certification_period_recipient_id_immutable`

최종 권한과 보존선:

- `erp_app`은 `recipient_service_plan_notice`의 `SELECT`만 가진다.
- `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`와 identity sequence의 `USAGE/UPDATE`를 회수한다.
- `erp_backup`은 read-only를 유지한다.
- table·sequence 소유관계·기존 행·PK/FK·date CHECK·replacement/audit 연결을 보존한다.
- 전후 행 수·PK 집합·전체 행 fingerprint·trigger 목록·권한을 검증한다.
- 옛 `service_plan_notice.py` 계산기는 활성 import·테스트에서 제거한다.

### 2.3 계약 projection

<a id="db-contract"></a>

`recipient_contract`의 신규 입력·응답은 `service_type_id`, `start_date`, `end_date`, `end_reason_text`만 사용한다. `service_start_date`와 서명자 3개 column/value는 보존하되 신규 입력·응답·판정에서 제외한다.

계약 종료일·종료사유 저장과 수급자 상태의 `계약종료` 수동전환은 별도 mutation이다. 어느 쪽도 다른 쪽을 자동실행하지 않는다. 계약·인정은 새 계획일정 저장의 필수 gate가 아니다.

## 3. S1 — 설정·계정·센터·감사

- 새 계정 table을 만들지 않고 `user_account`를 쓴다.
- `staff_id` UNIQUE 1:1을 유지한다. USER는 아직 계정에 연결되지 않은 기존 사회복지사·간호사 직원만 선택하며, 계정 생성 중 직원행을 새로 만들지 않는다.
- 최초 ADMIN의 기존 직원 연결은 표시만 하고 일반 재연결 기능을 만들지 않는다.
- PIN 재생성·사용중지는 `session_version`을 증가시킨다. 사용중지는 삭제가 아니라 `login_allowed=false`이며 유일 ADMIN은 중지할 수 없다.
- 계정 생성·닉네임·PIN 재생성·사용중지/해제는 감사하되 PIN 원문·hash·lookup 값은 남기지 않는다.
- `center`에는 nullable text `center_message_text` 하나만 추가한다. 별도 설정·버전 table은 만들지 않는다.
- 센터정보·한마디는 모두 조회, ADMIN만 수정한다.
- 감사로그 조회는 기존 `audit_event`를 사용하며 ADMIN 전용이다. 조회용 복제원장·queue를 만들지 않는다.

### 4.1 직원 민감정보 보존선

기존 `staff_sensitive_identity` 구조와 자료를 그대로 유지한다.

| column | 불변조건 |
|---|---|
| `staff_id` | PK/FK → `staff.id`; 직원당 0개 또는 1개 |
| `resident_number_ciphertext` | `bytea` NOT NULL, 길이 0 초과 |
| `resident_number_nonce` | `bytea` NOT NULL, 정확히 12 byte |
| `resident_number_key_version` | integer NOT NULL, 양수 |
| `resident_number_lookup_hmac` | `bytea` NOT NULL, 정확히 32 byte, 전역 UNIQUE |
| `encrypted_at_utc`, `updated_at_utc`, `row_version` | 시각과 양의 동시성 version |

평문 주민등록번호와 마스크 문자열 column을 추가하지 않고 암호문·nonce·HMAC·key
version을 공개 API나 감사 JSON에 노출하지 않는다. 승인된 정정은 해당 1:1 행을
`FOR UPDATE`로 잠근 뒤 암호문·nonce·key version·HMAC과 `row_version`을 한
transaction에서 바꾸며 전역 HMAC unique를 유지한다.

### 4.2 기존 원장 재사용

- 직원·수급자 일반 기본정보는 기존 원장을 사용하고 로그인 사용자 모두의 변경을 감사한다.
- 주민등록번호 reveal·정정은 공동 기본정보 권한으로 우회하지 않는다.
- 수급자 인정번호는 기존 인정 identity에서 읽는다.
- 직원 직종변경 UI·새 원장은 만들지 않는다. 직종변경은 퇴사 후 새 재직이다.
- 신규교육은 재직 ID별 새 행, 인권교육은 반기 key, 연간교육은 연도별 5과목, 보수교육은 연도별 완료를 기존 교육 원장에서 관리한다.
- 직원상담 신규 write는 `COMPLETE/INCOMPLETE`와 분기 key만 사용하도록 상세내용 필수 CHECK를 forward migration에서 제거한다. 기존 상세값·`EXEMPT` 행은 보존한다.
- 건강검진 신규 write는 `check_date`만 사용하고 `staff_health_check_requirement` 신규행을 자동생성하지 않는다.

### 4.3 수급자 완료 최소원장

반기평가를 제외한 네 버튼형 완료에만 다음 원장을 S2에서 추가한다.

| 신규 원장 | unique 업무 key | 저장값 |
|---|---|---|
| `recipient_counseling_reflection_completion` | 수급자+연도 | completed, audit, row_version |
| `recipient_document_check_completion` | 수급자+월 첫날 | completed, audit, row_version |
| `recipient_certification_expiry_completion` | 인정기간 ID | completed, audit, row_version |
| `recipient_contract_expiry_completion` | 계약 ID | completed, audit, row_version |

대상자 목록은 원천자료에서 계산하며 미리 복제하지 않는다. 원천 정정·무효화로 현재 대상에서 빠져도 과거 완료행과 감사는 cascade 삭제하지 않는다.
`recipient_document_check_completion` 원장은 S2에서 준비하되, 대상자 projection은
S4의 `service_schedule`이 생긴 뒤 활성화한다. 다른 달력자료를 대체 원천으로
쓰거나 S2에서 일정 원장을 선구현하지 않는다.

### 4.4 반기평가와 자동카드

`recipient_plan_notification`의 유효 `notified_date` 입력 자체가 반기평가 완료다. 별도 완료 boolean·업무행·W2 계약연결 row를 만들지 않는다. 잘못된 통보일은 물리삭제하지 않고 무효화한다.

다음 권장기한은 최근 유효 통보일에서 6개월이 되는 달의 말일과 현재 인정·계약 만료일 중 빠른 날이다. 통보일이 없으면 임의 날짜를 저장하지 않고 미완료로 projection한다. 계획적용 시작·종료 text는 날짜검증·저장거부에 쓰지 않는다.

계약만료·인정만료·반기평가·직원교체 카드는 각 원천과 완료값에서 계산한다. 카드용 범용 table, 단계, 담당자, 첨부, 복제 완료값을 만들지 않는다.

## 6. S4·S5 — 일정, Excel, 태그, 직원교체

### 6.1 전체 일정

S4는 `service_schedule`과 `service_schedule_provider` 두 원장만 추가한다.

- schedule: 수급자·서비스·날짜·시작·종료·row_version·감사
- provider: schedule+직원 unique
- 방문요양·방문목욕은 서로 다른 제공자 1명 또는 2명
- 다른 세 서비스에는 이번 결정만으로 제공자 수 상한을 만들지 않음
- 일정과 provider 집합은 한 transaction으로 변경
- 일시대체는 provider를 바꾸는 일반 수정
- 계약·인정·`care_assignment`를 필수 FK/gate로 쓰지 않음

다음 판정은 사용자 결정 전 `UNKNOWN`이므로 exclusion constraint나 허용정답을 만들지 않는다.

- 같은 요양보호사의 서로 다른 일정 겹침
- 같은 수급자의 서로 다른 일정 겹침
- 근무일의 재직·서비스자격 불일치

정상 2인 급여는 충돌이 아니다.

### 6.2 계획·태그 Excel

실제 가명 표본 전에는 sheet·header·식별키·parser column을 만들지 않는다. 표본 승인 뒤 S4/S5에서만 불변 원본과 원본행의 최소원장을 만든다.

- 원본 bytes 보호저장소 key·SHA-256·종류·파일명·가져온 계정·시각
- 원본행 번호와 가공 전 식별값·날짜·시작·종료
- 연결된 schedule과 자동수정 전후값
- 같은 SHA-256 태그 원본 중복 금지. 계획 Excel의 중복·대체 정책은 실제 표본 전 확정하지 않음
- 일반 파일함과 분리, 일반 파일 삭제의 cascade 대상 아님

`tag_import_applied_date`는 적용완료 날짜를 unique하게 기록한다. 이미 적용된 날짜는 다른 파일에서도 건너뛰고 새 날짜만 처리한다. 자동수정은 `SYSTEM/IMPORT` 감사로 원본행과 전후 schedule을 연결한다. 원본과 수정 전 값은 덮어쓰지 않는다.

범용 import 상태기계, lease, heartbeat, 재시도 queue를 만들지 않는다.

### 6.3 직원교체

S5에서 실제 제공순서가 확정되면 `staff_change_case` 하나만 추가한다. 수급자·서비스·새 직원·첫 제공일·기한(+13일)·완료·원인 제공묶음·Day14 재교체의 앞 case 예외종결 연결·audit·row_version만 둔다.

상담일·내용·사유·범용 단계상태는 두지 않는다. 실제 제공자 집합에 새로 들어온 사람마다 1건을 만들고 원천 정정·무효화 뒤 재판정한다. 이 원장은 직원교체 업무의 원천이지 카드 전용 복제원장이 아니다.

## 7. S6 — 실제 파일함

S6에서 `filebox_node` 하나와 보호된 실제 저장루트만 추가한다.

최소값은 parent, folder/file 구분, 표시이름, file의 내부 storage key·size·SHA-256, 휴지통 시각·행위자, row_version·감사다.

- 일반 파일함은 로그인 사용자 모두 공동 사용한다.
- 삭제는 영구삭제가 아니라 휴지통 이동이며 모두 복원할 수 있다.
- v1에는 file version, 영구삭제, 보존기간, GC queue를 만들지 않는다.
- 정규화한 최종경로가 지정 루트 안인지 확인하고 절대경로·상위경로·symlink·junction·reparse point 탈출과 parent 순환을 거부한다.
- 감사·시스템·가져오기 로그와 Excel 원본은 일반 파일함에서 보이거나 변경되지 않는다.
- `filebox_node` 변경이 import 원본·감사·시스템로그를 cascade하지 않는다.

## 8. 권한·DEFER·금지

공동 API는 로그인과 변경요청 CSRF를 검사하되 `AccountPermission` 부여행을 요구하지 않는다. 계정관리·감사로그·민감정보는 이 공동권한에 포함되지 않는다.

본인부담금·OCR·일반 입출력은 `DEFER`다. 기존 메뉴·table·자료를 삭제하지 않고 새 상세구조도 만들지 않는다. 외부 WorkCadence 연동, 임의 권한편집기, 새 인정전환, 계약연결형 급여계획서, 확정월·일괄취소, 일시대체 전용상태, 범용 업무카드/queue도 만들지 않는다.

## 9. migration·검증 gate

각 slice는 같은 후보 SHA에서 다음을 증명한다.

1. 현재 DB forward upgrade와 fresh install chain이 모두 성공한다.
2. 적용된 과거 migration hash와 기존 행·PK·fingerprint가 보존된다.
3. R0 뒤 W2 역사 table은 app read-only이고 정확히 다섯 전용 guard만 제거된다.
4. 반기평가 저장 완료증거가 `recipient_plan_notification` 하나뿐이고 카드 중복원장이 없다.
5. 계정 1:1·세션무효화·감사 비밀값 제외와 고정 권한이 mutation-sensitive하게 검증된다.
6. 공동기능 권한이 민감정보·연차·개인일정 경계를 우회하지 않는다.
7. 일정·Excel·직원교체는 확정된 결정·표본 범위만 구현한다.
8. 파일함 휴지통·복원·루트탈출 차단·원본 비연쇄삭제를 PostgreSQL과 Windows 경로에서 검증한다.
9. 해당 slice 밖 미래 table·상태·nullable FK가 catalog에 없다.
10. API·OpenAPI·브라우저가 비활성 column·table·옛 실행경로를 노출하지 않는다.

실행순서와 활성 결정 register는 [`06_개발로드맵_결정현황_v1.2.md`](06_개발로드맵_결정현황_v1.2.md)가 소유한다.

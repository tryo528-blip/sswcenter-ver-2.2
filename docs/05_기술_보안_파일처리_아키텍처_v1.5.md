## 1. 시스템 구성

### 1.1 운영 토폴로지

```text
센터 내부 PC 브라우저
        │ HTTPS
        ▼
로컬 Gateway
  ├─ React 정적파일
  └─ /api/* → FastAPI
                   ├─ PostgreSQL
                   ├─ 일반 파일함 저장소
                   └─ 불변 import 원본 저장소
```

- Windows 서버 PC 한 대에서 운영하는 내부망 전용 모듈형 모놀리스다.
- 외부 CDN·웹폰트·클라우드 업무 API 없이 인터넷 단절 상태에서도 동작한다.
- PostgreSQL과 FastAPI 내부포트는 사용자 PC에 공개하지 않는다.
- 프론트와 API는 같은 HTTPS origin을 사용한다.
- 사용자 브라우저와 파일 클라이언트가 DB에 직접 접속하지 않는다.
- 범용 queue·worker·lease·heartbeat 플랫폼은 현재 필수 구성요소가 아니다.

### 1.2 모듈 경계

- 도메인은 staff, recipient, contract, schedule, billing, files처럼 나누되
  하나의 배포단위와 DB transaction 경계를 공유한다.
- route는 인증·입출력 변환을, service는 업무검증·권한·transaction을,
  repository는 persistence를 담당한다.
- route에 SQL을 쓰거나 repository가 업무상태를 임의 결정하지 않는다.
- 특정 import에 제한된 보조 실행기가 나중에 승인되더라도 service의 typed
  command를 사용하고 자기 HTTP API나 직접 SQL로 업무사실을 바꾸지 않는다.

### 1.3 소스와 운영자료 분리

- 소스 저장소 안에 운영 DB·실제 첨부·비밀값·백업을 두지 않는다.
- 개발·테스트는 합성자료와 별도 DB·파일경로만 사용한다.
- 운영 runtime root는 production에서 필수인 절대경로 환경변수
  `SSWCENTER_DATA_ROOT`로 주입하며 운영 경로를 Git에 기록하지 않는다.
- 실제 파일과 DB는 함께 백업·복구할 수 있는 논리적 복구단위다.

## 2. 프론트엔드·백엔드 기준

### 2.1 프론트엔드

- React + TypeScript + Vite를 사용한다.
- 운영은 빌드된 정적파일만 제공하며 Vite 개발서버를 실행하지 않는다.
- TypeScript strict, ESLint, 생성된 OpenAPI 타입을 사용한다.
- 서버 상태와 UI 상태를 분리하고 저장 성공 전 완료처럼 표시하지 않는다.
- API 응답을 `any`나 수동 단언으로 우회하지 않는다.
- 프로젝트 공통 CSS와 필요한 소형 컴포넌트를 우선하며 MUI 같은 대형 UI
  framework를 기본 의존성으로 두지 않는다.
- PWA·모바일 설치형 앱은 현재 범위가 아니다.
- 사이드바 메뉴와 공개 상호작용은 03이 소유한다.

### 2.2 백엔드

- FastAPI 모듈형 모놀리스와 SQLAlchemy·Alembic을 사용한다.
- 동기 DB 접근을 기본으로 하며 비동기화는 측정된 병목이 있을 때만 승인한다.
- 여러 테이블을 바꾸는 업무명령은 service의 한 transaction에서 처리한다.
- 파일 읽기·변환처럼 시간이 걸리는 실행 중 DB transaction을 잡고 있지 않는다.
- 공식 규칙은 시행일·근거·규칙버전과 함께 순수함수로 격리한다.
- 공식 원문은 출처 식별자·시행일·조항/부록과 원본 bytes의 SHA-256을 함께
  보존하여 같은 URL의 문서가 교체되어도 당시 규칙 입력을 재현할 수 있어야 한다.
- 공식 원문이나 승인된 정책이 없는 수가·가산·대상판정은 활성화하지 않는다.

### 2.3 의존성과 설정

- Python·Node 의존성은 lock 파일로 고정하고 취약점·라이선스 검토 뒤 갱신한다.
- 비밀값은 환경별 외부 secret 저장소에서 읽고 로그·오류에 출력하지 않는다.
- development, test, production 설정을 분리한다.
- production에서 개발 우회·합성 key·debug가 감지되면 기동을 거부한다.

## 3. 공개 API 공통계약

### 3.1 형태와 책임

- REST JSON, 기본 prefix `/api/v1`, same-origin HTTPS를 사용한다.
- 운영 CORS 허용목록은 비워두며 외부 공개 API와 GraphQL은 만들지 않는다.
- 업무 중심 request/response를 사용하고 DB 컬럼을 그대로 노출하지 않는다.
- 대량 목록은 서버 페이지네이션과 결정적 정렬을 사용한다. 마지막 정렬키는
  안정 PK다.
- 변경명령은 권한·CSRF·예상 `row_version`을 검사한다.

### 3.2 표준 오류 봉투

```json
{
  "error": {
    "code": "PERIOD_OVERLAP",
    "message": "기간이 기존 자료와 겹칩니다."
  },
  "field_errors": [],
  "details": {},
  "request_id": "..."
}
```

| 상태 | 의미 |
|---|---|
| `400` | 명시적으로 거부한 비검증 request framing·명령 봉투 오류 |
| `401` | 미인증 |
| `403` | 권한·CSRF 거부 |
| `404` | 대상 없음 |
| `409` | version·unique·현재상태 충돌 또는 동시경쟁 DB 제약 충돌 |
| `415` | 지원하지 않는 media type |
| `422` | `RequestValidationError` 또는 사용자가 입력을 고쳐 재시도할 수 있는 업무검증 실패 |
| `429` | 로그인·요청 제한 |
| `500` | 예상하지 못한 서버 오류 |

- FastAPI `RequestValidationError`에는 JSON body decode와 schema field 오류를
  포함하며 같은 봉투의 `VALIDATION_ERROR`를 사용한다.
- 정상 사전검증에서 발견한 기간중복·containment·대체집합 오류는 422다.
  같은 검증을 통과한 뒤 동시경쟁으로 DB 제약이 깨진 경우는 409다.
- DB 오류·SQL·stack trace를 브라우저에 노출하거나 500으로 방치하지 않는다.
- 공통 안정코드는 `VALIDATION_ERROR`, `ROW_VERSION_CONFLICT`,
  `PERIOD_OVERLAP`, `PERIOD_CONTAINMENT_FAILED`다.
  도메인별 코드는 02의 의미와 OpenAPI 계약테스트가 소유하며 한 번 공개한
  의미를 재사용하지 않는다.

### 3.3 낙관적 잠금·멱등성

- 409에서는 서버 최신 version, 가능한 `conflict_fields`, 재조회 가능정보를
  `details`에 주고 UI는 입력값을 보존한다. 비충돌 필드만 재적용하고 동일 필드는
  사용자 선택 없이 덮어쓰지 않는다.
- 일반 변경명령은 예상 `row_version`으로 경쟁수정을 막는다.
- 태그 Excel은 원본 SHA-256 중복검사와 날짜별 최초 반영 표식으로 재실행을
  통제한다. 같은 hash는 중복이며, 한 번 태그를 반영한 날짜의 후속 태그 import는
  수정본이라도 건너뛴다. 계획 Excel의 재가져오기 의미는 실제 표본 전 추측하지
  않는다.
- 범용 preview/apply·월 확정·일괄작업·OCR를 전제로 한 공통 멱등키 플랫폼은
  현재 계약이 아니다. 새 비동기 기능이 실제로 승인될 때 그 명령에 필요한
  최소 키와 재시도 의미를 별도로 확정한다.

## 4. PostgreSQL 구현 기준

### 4.1 역할·자료형

```text
erp_owner   schema 소유·migration 전용
erp_app     애플리케이션 DML
erp_backup  백업·복원검증
```

- 애플리케이션은 슈퍼유저로 접속하지 않는다.
- 내부 PK는 bigint identity, 업무일자는 date, 사건시각은 timestamptz UTC,
  금액은 bigint 원 단위, 기간은 range를 사용한다.
- 서비스월은 date로 저장하고 월 1일 CHECK를 둔다.
- 화면 날짜는 `Asia/Seoul` 기준으로 계산한다.

### 4.2 transaction·동시성

- 기본 격리수준은 `READ COMMITTED`다.
- 여러 aggregate를 바꾸는 명령은 한 transaction으로 처리한다.
- 번호발급·revision 증가처럼 실제 경쟁구간이 확인된 명령만 row lock 또는
  transaction advisory lock을 사용한다.
- 사용자 메시지는 service가 먼저 판정하고 DB는 구조적 무결성의 최종
  방어선으로 남긴다.
- 기간중복은 GiST exclusion, 유효행 중복은 partial unique, 부모·자식 기간은
  필요한 최소 deferrable constraint trigger로 보호한다.

### 4.3 명명계약

- PK·FK·UNIQUE·CHECK·index는 `pk_`, `fk_`, `uq_`, `ck_`, `ix_`다.
- exclusion은 `ex_`, DB function은 `fn_`다.
- deferrable constraint trigger는 `ct_`, ordinary trigger는 `trg_`다.
- ORM metadata·Alembic·실제 catalog의 exact 이름을 같은 schema test에서
  비교하며 alias로 취급하지 않는다.

<a id="migration"></a>

### 4.4 migration

- 적용된 Alembic revision은 수정하지 않고 새 revision을 추가한다.
- Wave 하나는 필요한 만큼의 선형 revision chain을 가질 수 있다.
- upgrade 전 backup·preflight, 후 catalog·FK·constraint·핵심 query를 검사한다.
- downgrade가 안전하지 않으면 명시적 복구·restore 절차를 제공한다.
- 데이터 손실·이관·권한·암호변경 migration은 HIGH로 분류한다.
- 개발·테스트·운영 DB를 분리하고 PostgreSQL 통합테스트를 SQLite로 대체하지
  않는다.

## 5. 인증·권한·보안

### 5.1 PIN 로그인

- PIN은 숫자 6자리 이상이며 원문을 저장하지 않는다.
- Argon2id hash, 서버측 pepper, 식별용 HMAC을 분리한다.
- 로그인 식별자가 PIN뿐이므로 `pin_lookup_hmac`은 전체 계정에서 UNIQUE이며
  서로 다른 사용자가 같은 PIN을 공유할 수 없다.
- 식별 계정 5회 연속 실패는 15분 잠금이다.
- 동일 기기·IP의 미식별 실패는 15분 안에 10회, 서버 전체는 30회에서
  15분 제한한다.
- 자동로그인·remember-me·영속 인증쿠키는 제공하지 않는다.
- 성공·실패·잠금·해제를 PostgreSQL에 감사한다.

### 5.2 세션·CSRF

- 브라우저에는 임의 session token 쿠키만 두고 DB에는 hash와 만료·폐기를 둔다.
- 쿠키는 `Secure`, `HttpOnly`, `SameSite=Strict` 또는 동등한 정책을 사용한다.
- 로그인 때 session ID와 CSRF token을 회전하고 유휴·절대 만료를 적용한다.
- 모든 상태변경과 로그아웃은 POST + CSRF다.

### 5.3 권한

- 백엔드가 최종 권한을 판정하며 버튼 숨김은 보안경계가 아니다.
- `ADMIN`은 센터장·관리책임자이고 `USER`는 사회복지사·간호사다. 간호사는
  별도 탭·별도 배정체계 없이 사회복지사와 같은 계정·업무 흐름을 사용한다.
- 로그인 사용자는 모두 수급자·직원 명단과 기본정보, 5개·6개 완료현황,
  전체 수급자-요양보호사 일정, 계획·태그 Excel 가져오기, 사회복지사 담당배정,
  일반 파일함을 조회·변경할 수 있다. 이 공동권한에는 `AccountPermission`을
  조회하거나 적용하지 않는다.
- 전체 일정과 공동정보 변경은 모두 감사한다. 주민등록번호 등 민감정보의
  별도 마스킹·reveal·access event는 공동권한과 무관하게 유지한다.
- 사회복지사 방문일정은 사회복지사를 선택하면 로그인 사용자 모두 조회하되,
  선택된 사회복지사 본인과 `ADMIN`만 생성·수정·삭제할 수 있다.
- 사회복지사 연차는 본인과 `ADMIN`만 조회하고 작성자 본인만 생성·수정·삭제한다.
  `ADMIN`의 권한은 조회뿐이다.
- 개인 할 일·개인 일정은 작성자 본인만 조회·생성·수정·삭제한다. owner는
  로그인 세션에서 서버가 정하며, 다른 사용자와 `ADMIN`의 목록·검색·집계
  응답에는 행의 존재 자체가 나타나지 않는다. 제목·본문·시각·완료값 등 개인
  일정의 내용과 event는 `AuditEvent`에도 남기지 않는다.
- 설정의 계정관리·감사로그·백업 명령은 `ADMIN` 전용이다. 센터 기본정보와
  센터 한마디는 로그인 사용자 모두가 조회하고 `ADMIN`만 변경한다.
- 일반 파일함은 모든 로그인 사용자가 자유롭게 사용하지만 import 감사원본과
  시스템 원본 저장소는 일반 파일함 권한으로 열거나 지울 수 없다.
- 민감조회·출력·다운로드는 access event를 남긴다.

### 5.4 개발 우회와 보안 header

- 개발 우회는 development·test의 합성 DB와 개발전용 계정에서만 허용한다.
- production backend와 build에 우회 route·버튼·설정을 포함하지 않는다.
- gateway는 CSP, `X-Content-Type-Options`, `Referrer-Policy`,
  `frame-ancestors`, 적절한 `Permissions-Policy`를 설정한다.
- HSTS는 HTTPS host와 인증서 운영이 안정화된 뒤 활성화한다.
- 개인정보 응답은 `Cache-Control: no-store`다.

### 5.5 주민등록번호 암호화·정정

- 업무 입력·정정은 [02 §3.2](02_업무규칙_계약_v1.1.md), 화면은
  [03 §3.2](03_UI_API_상호작용_계약_v1.2.md), DB 보존선은
  [04 `db-staff-sensitive`](04_데이터_DB_불변조건_v4.8_PostgreSQL.md#db-staff-sensitive)가
  소유한다. 암호화·reveal 보안은 이 절이 소유한다.
- 정규화 13자리는 AES-256-GCM으로 암호화하며 매번 CSPRNG 새 12-byte nonce를
  사용한다.
- AAD는 `staff:{staff_id}:resident-number:v{key_version}`다. 같은 직원 정정도
  새 nonce로 다시 암호화하므로 AAD 재사용은 허용하되 nonce는 절대 재사용하지
  않는다.
- AES key는 version별 32-byte, lookup HMAC-SHA-256 key는 별도 안정 32-byte
  secret이다. key는 DB·Git·일반 설정파일에 두지 않고 Windows Credential
  Manager 또는 DPAPI로 보호된 secret 저장소에서 읽는다.
- 관리자 reveal은 전용 POST + CSRF + 현재 PIN step-up을 요구한다. 성공 응답은
  no-store이며 성공 1회당 access event 1건을 남긴다.
- HMAC key rotation은 offline exclusive maintenance에서 전체 재계산·unique
  검증 뒤 전환한다.
- 평문·암호문·nonce·HMAC을 로그·감사 JSON·오류·trace·fixture·snapshot에
  기록하지 않는다.

## 6. 파일·입출력·OCR 경계

### 6.1 현재 범위

| 영역 | 현재 지위 | 최소 계약 |
|---|---|---|
| 일반 파일함 | `IMPLEMENT` | 탐색기형 폴더·파일 관리 |
| 공단 계획 Excel | `IMPLEMENT`, parser 대기 | 실제 샘플을 받은 뒤 정확한 열 계약 확정 |
| 공단 태그 Excel | `IMPLEMENT`, parser 대기 | 원본 보존과 확정된 30분 보정 규칙 적용 |
| OCR | `DEFER / OUT-OF-SCOPE` | 메뉴는 유지하되 활성 API·적용 흐름을 만들지 않음 |
| 그 밖의 범용 입출력 | `DEFER / OUT-OF-SCOPE` | 메뉴는 유지하되 범용 import/export 플랫폼을 만들지 않음 |

OCR과 입출력은 삭제 대상이나 의미변경 대상이 아니다. 후속 사용자 결정과 실제
샘플이 생길 때까지 비활성 경계로 두며, 아래 안전조건도 후속 활성화를 위해
보존한다. 다만 현재 기능 때문에 OCR 필드, 범용 입력 enum, 출력 서식 또는 공통
queue를 미리 확정하거나 S0~S6 완료조건으로 강제하지 않는다.

### 6.2 일반 파일함

- 일반 파일함은 탐색기처럼 폴더 생성·이름변경·이동·휴지통 이동·복원과 파일
  업로드·다운로드·열기·이름변경·이동·휴지통 이동·복원을 제공한다.
- 모든 로그인 사용자가 같은 일반 파일함을 조회·변경할 수 있고 모든 변경을
  감사한다. 감사에는 사용자·시각·행위·대상 ID·변경 전후 **논리 경로**를
  기록하되 서버 절대경로와 파일본문은 기록하지 않는다.
- 1차 범위에는 영구삭제, 버전관리, 보존기간 자동처리, GC가 없다. 휴지통도
  복원 가능한 상태로 보존한다.
- 서버는 정규화한 대상 경로가 승인된 일반 파일함 root 안에 있는지 매 작업마다
  확인하고 `..`, 절대경로 주입, symlink·junction·reparse point를 통한 root
  이탈을 거부한다.
- 업로드는 임시영역에서 크기·hash를 계산하고 안전한 최종 publish 뒤 DB 사실을
  확정한다. 실패 시 DB와 파일 중 한쪽만 성공한 상태를 남기지 않는다.
- 일반 파일함과 import 원본 저장소는 논리·물리적으로 분리한다. 일반 파일함의
  이동·휴지통·복원이 import 원본, import 감사이력 또는 시스템 원본을 cascade
  변경하거나 삭제해서는 안 된다.

### 6.3 계획·태그 Excel 원본과 태그 반영 이력

- 수신 원본 bytes는 불변이며 SHA-256, 크기, 수신시각, 로그인 사용자, 입력종류와
  함께 보존한다. 수정된 파일은 새 원본이다.
- parser가 읽은 원본 행은 원본 hash, 시트, 행번호, 셀 문자열과 함께 불변으로
  보존한다. 감사·기술 로그에는 전체 Excel 행이나 개인정보를 복사하지 않는다.
- 한 원본 행이 어느 계획일정·태그와 연결되었고 반영 전후 값이 무엇이었는지
  식별 가능해야 한다. 원본과 사람이 나중에 고친 일정은 모두 남겨 서로
  덮어쓰지 않는다.
- 같은 SHA-256 **태그 원본**은 중복으로 처리한다. 한 번 태그를 반영한 날짜는
  뒤에 같은 날짜의 수정 태그 Excel을 다시 가져와도 건너뛴다. 최초 반영 뒤
  계획일정은 사람이 자유롭게 고칠 수 있고, 이후 사람의 수정도 기존 원본·보정
  이력을 지우지 않는다. 계획 Excel의 중복·대체 정책은 실제 표본으로 확정한다.
- 계획·태그 Excel 가져오기와 반영은 모든 로그인 사용자가 할 수 있고 실행자,
  원본 ID, 대상 날짜, 적용·건너뜀·확인요망 건수를 감사한다.

### 6.4 계획 Excel parser 착수조건

- 계획일정 Excel의 시트명·열명·자료형·날짜범위와 행 식별방법은 제공된 실제형
  가명 샘플과 기대결과로 확정한다. 샘플이 없으면 이름이나 위치를 추측하지 않는다.
- 같은 수급자·요양보호사·날짜·시작·종료시간은 하나의 계획일정을 식별하는
  기본 사실이다. 가져온 뒤에는 전체 일정의 일반 수정·삭제와 같은 권한·감사
  계약을 적용한다.
- workbook은 `.xlsx`를 기본으로 하며 macro를 실행하지 않는다. 다른 형식 지원은
  실제 샘플과 안전 parser가 별도로 승인될 때까지 추가하지 않는다.

### 6.5 태그 매칭과 시간 보정

- 태그는 같은 수급자·요양보호사·날짜의 계획 후보 중 **정확히 하나**와만 짝이
  확정될 때 자동 보정한다. 계획 한 행과 태그 한 행은 각각 최대 한 번만 사용한다.
- 기준 계획 시작시각을 `P`라 할 때 태그 시작이 `P-59~P-30분`이면 `P-30분`,
  `P-29~P+29분`이면 `P`, `P+30~P+59분`이면 `P+30분`으로 보정한다.
  정확히 `±60분`부터는 자동 보정하지 않는다.
- 서비스 총시간은 30분 단위로 내림하고 최대 480분으로 제한한다. 예를 들어
  180~209분은 180분, 210~239분은 210분이다. 30분 미만이면 자동 보정하지 않는다.
  종료시각은 보정한 시작시각에 이 서비스시간을 더해 계산하며 시작·종료를 한
  transaction에서 함께 바꾼다.
- 종료 태그 없음, 계획만 있음, 태그만 있음, 시간차가 범위를 벗어남, 30분 미만,
  비정상값, 후보가 없거나 둘 이상이라 애매함은 일정표에 모두 `확인요망`으로만
  표시하고 일정을 자동 변경하지 않는다. 계획만 있음은 업로드 원본이 실제로
  덮는 날짜 안에서만 판정하고, 태그만 있음은 가짜 계획일정을 만들지 않는다.
- 자동보정 감사의 행위자는 `SYSTEM/IMPORT`로 구분하고 가져오기를 실행한 계정,
  원본·원본행, 일정 전후값을 함께 연결한다.
- 수동으로 고친 계획도 다음 **최초 반영 가능한 날짜 import**가 정확히 매칭되면
  다시 보정할 수 있고 사람은 그 결과를 다시 자유롭게 고칠 수 있다. 다만 이미
  반영된 날짜의 재업로드는 §6.3에 따라 건너뛴다.

### 6.6 직원교체 판정

- 같은 수급자·서비스의 시간순 실제 급여에서 같은 날짜·시작·종료 행을 제공자
  집합 하나로 묶고 직전 집합에 없던 새 제공자마다 직원교체 1건을 만든다.
  `A+B → A+C`이면 C만 대상이며 빠진 사람만 있으면 새 건을 만들지 않는다.
  방문요양과 방문목욕의 정상 2인 급여 자체는 직원교체가 아니다.
- 일시 대체근무도 제공자 집합이 달라지므로 직원교체다. 계획일정만 편집했거나
  담당배정만 바뀐 경우에는 직원교체 업무카드를 만들지 않는다.
- 정확한 업무카드 대상기간과 완료규칙은 02가 소유하고, 원본·매칭·변경 이력은
  이 절의 파일처리 계약을 따른다.

### 6.7 DEFER 영역의 보존된 안전조건

- 범용 입출력을 나중에 활성화하면 원본, 정규화 결과, 사용자 검토, 적용대상과
  실패를 재현 가능하게 보존한다. 실제 상태 enum·API·대체 snapshot 정책은
  그때의 실제 샘플과 사용자 결정으로 확정한다.
- OCR을 나중에 활성화하면 실제 추출필드는 가명 실제형 샘플로 확정하고 후보
  추출과 업무반영 사이에 필드별 검토·선택·명시 승인을 둔다.
- OCR 적용 command는 권한·CSRF·대상 `row_version`·후보 version을 다시
  검사하고 승인한 적용 묶음과 감사를 한 transaction에서 기록한다. stale·중복
  불일치·실패 시 업무변경은 0건이어야 한다.
- OCR·입출력 adapter가 직접 SQL, repository 우회 commit, 자기 HTTP 호출로
  업무사실을 변경하지 않는다.
- `.xlsm`·`.xlam` macro를 실행하지 않는다. 구형 형식 지원은 승인된 안전 parser와
  가명 회귀샘플이 있을 때만 추가한다.

<a id="worker"></a>

## 7. 제한된 실행과 DEFER

- 현재 범위는 범용 durable worker, 공통 queue, attempt·lease·heartbeat,
  범용 재시도·취소 상태기계, Download Inbox Agent를 요구하지 않는다.
- 계획·태그 가져오기는 우선 요청 안에서 제한된 작업으로 구현할 수 있다. 실제
  파일 크기·처리시간 때문에 비동기 실행이 필요하다는 증거가 생기면 해당 import에
  필요한 최소 run 상태와 중복방지만 별도 승인한다.
- Windows Task Scheduler는 현재 제품 업무의 필수 구성요소가 아니다. 정기 업무는
  DB의 업무카드와 달력 표시로 관리하며, 파일을 자동 수집·이동·삭제하지 않는다.
- OCR·범용 입출력이 후속 범위로 승인되기 전에는 그 기능을 이유로 worker나
  queue schema를 먼저 만들지 않는다.
- 이는 기존 기반을 삭제하라는 뜻이 아니다. 후속 승인 기능이 실제로 비동기
  실행을 사용하면 DB queue의 원자적 선점, 짧은 선점 transaction, 멱등 실행,
  attempt·lease·heartbeat·timeout·재시도·취소 이력과 장애복구를 보장한다.
- Download Inbox Agent도 `DEFER`다. 나중에 승인되면 수동 업로드를 대체경로로
  유지하고 임시·잠김·크기변화 파일을 건너뛰며, 실패한 파일을 자동 이동·삭제하지
  않는다.

<a id="windows-deploy"></a>

## 8. Windows 운영·네트워크

- PostgreSQL, Gateway, Web은 시작 시 자동 실행하고 실패 재시작과 기술 로그를
  설정한다. DEFER인 Worker·Download Agent를 현재 필수 자동시작 대상으로 두지
  않는다.
- 후속 승인된 제한 실행기가 추가되면 권한·복구·기술 로그를 그 실행기 범위에
  맞게 별도 확정한다.
- gateway는 내부 HTTPS 종단, React 정적파일, `/api/*` reverse proxy와 보안
  header를 담당한다.
- 서버는 고정 내부 IP/호스트명을 사용하고 방화벽은 센터 내부 HTTPS만 허용한다.
- 공유기 포트포워딩·공인망 공개·클라우드 터널을 사용하지 않는다.
- 운영 서비스는 인터넷 없이 정상동작하고 일반 브라우저를 관리자 권한으로
  실행하지 않는다.
- Wi-Fi 모바일·태블릿 지원은 범위 밖이다.

<a id="backup-restore"></a>

## 9. 백업·복원·재해복구

### 9.1 매체 역할

- 운영 DB와 운영 파일은 서버 내부 SSD에 둔다.
- 실제 기관자료의 암호화 백업은 별도 USB에 둔다.
- 오프라인 설치파일·릴리스·복원도구는 재해복구용 외장 SSD에 둔다.

### 9.2 같은 복구단위

백업 묶음:

- PostgreSQL custom-format dump
- 일반 파일함의 파일·폴더 metadata와 실제 bytes
- 불변 계획·태그 Excel 원본, 원본 행·반영연결 manifest와 실제 bytes
- 공식 출력물
- Alembic revision·릴리스 버전
- 전체 SHA-256 manifest와 검증결과

DB와 파일의 시점이 어긋난 백업을 정상으로 판정하지 않는다.

### 9.3 복원검증

- 운영 DB를 덮지 않고 임시 PostgreSQL과 임시 파일경로에 실제 복원한다.
- 운영 전, 큰 업데이트 후, 이후 반기마다 검증한다.
- migration revision·FK·핵심 건수·업무불변조건·DB↔파일 hash를 확인한다.
- 마지막 성공시각을 설정 화면에 표시한다.
- 실제 경로·세대수·암호키 책임자·복원훈련 책임은 운영 도입 때 별도 승인한다.
  이는 현재 S0~S6의 활성 결정·입력 register 항목이 아니다.

<a id="logging-health"></a>

## 10. 로그·감사·상태점검

- 감사로그는 PostgreSQL 업무원장, 기술 로그는 단기 진단파일이다.
- 일반·gateway·PostgreSQL 로그 기본 30일, 오류 90일, 설치·업데이트 180일을
  기준으로 회전·압축한다.
- PIN·주민등록번호·session token·파일본문·전체 Excel 행을 기록하지 않는다.
- redaction은 validation 오류·예외·audit JSON·access detail·테스트에도 같다.
- 모든 HTTP 요청에 request ID를 부여하고 오류응답·서버로그·활성 import 실행
  ID를 연결한다. DEFER 기능의 worker·OCR run ID는 그 기능이 활성화될 때만
  적용한다.
- 개인 할 일·개인 일정은 기술 오류의 request ID 이상으로 업무내용을 감사하지
  않는다. 제목·본문·시각·완료값과 생성·수정·삭제 event를 `AuditEvent`에 남기지
  않으며 `ADMIN`도 조회할 수 없다.
- `/health/live`는 프로세스 생존, `/health/ready`는 DB·필수경로·migration을
  확인한다. readiness 실패 시 쓰기를 받지 않는다.
- 외부 인터넷 모니터링에 운영정보를 보내지 않는다.

## 11. 품질·릴리스·금지사항

### 11.1 코드·테스트 안전

- Python은 Ruff·type check·pytest, TypeScript는 strict·ESLint·unit test를
  통과한다.
- PostgreSQL 제약은 실제 PostgreSQL에서, UI는 지원 viewport와 Playwright에서
  검증한다.
- 운영 host·DB명·경로가 테스트 설정에 들어오면 즉시 실패한다.
- 실제 개인정보·운영 파일을 fixture·snapshot·trace·screenshot에 넣지 않는다.
- 업무규칙 변경과 무관한 refactor를 한 diff에 섞지 않는다.
- 공동권한 API는 `AccountPermission` 행이 전혀 없는 `USER`도 성공하는지,
  개인 일정은 다른 사용자와 `ADMIN` 응답·검색·집계·`AuditEvent`에 나타나지
  않는지 계약테스트한다.
- 파일함은 root 이탈·symlink·junction·reparse point 거부, 논리경로 감사,
  휴지통 복원과 영구삭제 API 부재를 검증한다.
- 계획 import는 실제 표본 parser·원본·수동수정·감사를 검증한다. 태그 import는
  원본 hash 불변성, 원본행-반영행 연결, 같은 hash 중복, 반영된 날짜 재업로드
  건너뜀, 30분 경계와 확인요망을 mutation-sensitive하게 검증한다.

### 11.2 릴리스·업데이트

- 릴리스에는 frontend dist, backend 고정 의존성, migration, 서비스·gateway
  설정, 설치·검증 script, release hash manifest와 정본 버전을 포함한다.
- 업데이트 전 사용자 안내·운영 백업·migration preflight를 수행하고 쓰기를
  중지한 뒤 migration·배포·health·smoke 순서로 진행한다.
- 교체 실패는 이전 release로, migration 복구 불가 시 DB와 파일을 같은 사전
  백업으로 복원한다.
- 적용된 migration을 편집해 되돌리지 않는다.

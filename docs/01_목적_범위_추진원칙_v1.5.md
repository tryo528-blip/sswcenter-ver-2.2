# SSWCenter v2.2-alpha 목적·범위·추진원칙 v1.5

> 기준일: 2026-08-12 KST

## 1. 프로젝트 정의와 최상위 목적

SSWCenter ERP는 국민건강보험공단 전산을 대체하거나 복제하는 시스템이 아니다.
방문요양기관의 수급자·직원·일정 정보를 바탕으로 평가 대상과 해야 할 업무를
놓치지 않게 하고, 일정관리와 사회복지사 업무 완료까지 연결하는 기관 내부
운영 시스템이다.

제품 목적은 다음 세 축으로 고정한다.

1. **평가 대상 및 평가업무 관리**: 현재 누가 관리 대상인지와 완료·미완료
   여부를 빠르게 확인한다.
2. **수급자–요양보호사 일정관리**: 공단 Excel 계획일정을 가져온 뒤 기관 안에서
   수정하고 실제 태그와 비교·보정한다.
3. **사회복지사 업무흐름 관리**: 방문일정, 자동 마감, 개인 일정과 연차를
   달력에서 놓치지 않게 한다.

새 기능은 위 세 축 중 하나를 직접 개선할 때만 추가한다. “공단 전산에 있으므로
우리도 만든다”는 이유만으로 공단의 업무 판단·검증·청구 기능을 구현하지 않는다.

## 2. 메뉴와 최소기능 원칙

### 2.1 메뉴는 유지한다

대시보드, 수급자, 직원, 사회복지사, 본인부담금, 입출력, 파일함, 설정 메뉴는
이름과 자리를 유지한다. 기존 대시보드는 유지하되 대시보드 안의 `내 할 일`만
제거한다. 대시보드에 사회복지사 달력 이동 링크를 새로 만들지 않는다.
별도의 외부 앱 또는 WorkCadence 연동은 사용하지 않는다.

### 2.2 화면은 사람이 놓치지 않을 만큼만 만든다

- 수급자·직원 완료현황은 **대상자 이름과 완료/미완료 상태**를 기본으로 보여준다.
- 완료목록에는 발생 이유, 기준일, 기한, 담당자, 완료자·완료시각, 상세화면 링크,
  일정표 링크를 추가하지 않는다.
- 프로젝트 전반에서 체크박스를 완료 수단으로 사용하지 않는다. 다만 기존
  `보호자를 납부자로 지정` 선택은 예외로 인정한다.
- 날짜와 기한은 자동카드 계산·달력 배치·감사 등 내부 처리에는 사용할 수 있으나,
  완료목록 화면에 과잉 필드로 노출하지 않는다.
- 범용 업무큐, 여러 조치단계, 첨부 의무, 숨은 미래 상태를 먼저 만들지 않는다.

## 3. 제품·운영 범위

- React + TypeScript + Vite 프론트엔드
- FastAPI + Python 백엔드
- PostgreSQL + Alembic
- Windows 단일 서버
- 센터 내부망의 데스크톱·노트북 브라우저
- 외부 CDN·웹폰트·클라우드 업무 API 없이 인터넷 단절 상태에서도 정상동작
- 운영 DB는 서버 내부 SSD, 실제 데이터 백업은 별도 USB, 오프라인 설치·복구
  도구는 재해복구용 외장 SSD에 보관

세부 기술·보안·배포·복구와 파일함·OCR·입출력 경계는
[05 기술·보안·파일처리 정본](05_기술_보안_파일처리_아키텍처_v1.5.md)이
단일 원문이다.

## 4. 현재 확정 기능

### 4.1 완료현황

수급자 완료현황은 상담반영, 반기평가, 서류미비, 인정만료, 계약만료 5종이다.
직원 완료현황은 보수교육, 직원상담, 인권교육, 연간교육, 건강검진, 신규교육
6종이다. 정확한 대상자와 완료 규칙은
[02 업무규칙 정본](02_업무규칙_계약_v1.1.md)이 정의한다.

### 4.2 자동 업무카드

현재 확정된 카드는 계약만료, 인정만료, 반기평가, 직원교체 네 종류다. 원천
데이터와 완료 사실에서 계산하며 별도의 범용 카드 원장을 중복 생성하지 않는다.
카드 화면은 대상자, 업무명, 기한 또는 D-day, 완료 여부만 사용한다.

기존 `신규수급자`, `신규직원`, `퇴사직원`, `수급자종료` 카드의 유지·보류
여부는 아직 결정하지 않는다.

### 4.3 일정·사회복지사·파일함

- 방문요양, 방문목욕, 일시재가, 병원동행, 바로돌봄을 모두 사용한다.
- 전체 수급자–요양보호사 계획일정은 로그인 사용자 모두가 보고 수정할 수 있으며
  변경 로그를 남긴다.
- 사회복지사 메뉴는 선택한 사회복지사의 담당 수급자와 월 1회 방문일정을
  보여주는 달력 중심 화면으로 만든다.
- 계획 Excel과 실제 태그 Excel은 서로 다른 입력이다. 계획은 전체 일정의
  출발점이고 태그는 명확히 짝이 맞는 일정만 30분 단위로 보정한다.
- 파일함은 탐색기와 같은 폴더·파일 보관 기능으로 만들고, 로그 영역을 제외한
  일반 파일은 로그인 사용자 모두가 사용한다.

## 5. 재정렬 추진 순서

기존 구현을 전부 폐기하거나 처음부터 다시 만들지 않는다. 현재 바이트를 새
목적에 맞춰 다음 순서로 정렬한다.

| 단계 | 범위 | 완료 방향 |
|---|---|---|
| S0 | 활성 정본과 수용기준 정렬 | 새 3축, 최소기능, 보존·퇴역 경계를 문서에 반영 |
| R0 | 과잉 실행경로 퇴역 | 인정전환 실행기능과 옛 W2 급여계획서 실행경로 제거, 기존 이력 보존 |
| S1 | 설정·계정 | 센터장/사용자 계정, 직원 연결, PIN, 센터정보, 감사로그 |
| S2 | 기본정보·완료현황·단순카드 | 직원 수정, 수급자 인정표시, 수급자 5종·직원 6종, 만료·반기 카드 |
| S3 | 사회복지사 달력 | 담당연결, 방문일정, 자동마감, 연차, 개인 일정 |
| S4 | 계획일정 | 공단 계획 Excel 가져오기, 전체 일정 조회·수정 |
| S5 | 실제 태그와 직원교체 | 태그 Excel 보정·확인요망, 직원교체 산정과 카드 |
| S6 | 파일함 | 탐색기형 폴더·파일, 휴지통·복원, 감사 |

`서류미비` 완료원장은 S2에서 준비하지만 대상자는 S4의 수급자–요양보호사
`service_schedule`에서 계산한다. 따라서 S2의 다른 기능은 먼저 진행하되 S2 전체
봉인은 S4 일정 원장·수동 CRUD가 생긴 뒤 닫는다. 실제 Excel parser 표본은 이
의존성의 선행조건이 아니다.

기존 구현은 기능 단위로 `KEEP`, `MODIFY`, `MOVE TO SOCIAL-WORK HUB`,
`DROP / DEFER` 중 하나로 판정한다. 활성 기능에서 제외한다고 기존 사실·감사·
마이그레이션 이력을 임의 삭제하지 않는다.

## 6. 교차 구현 안전 원칙

### 6.1 실체와 기간 사실을 분리한다

- 직원·수급자는 하나의 실체다.
- 입·퇴사, 계약, 인정, 등급, 급여종류는 기간을 가진 별도 사실이다.
- 재입사와 재계약은 기존 행을 덮어쓰지 않고 새 기간 행을 추가한다.

### 6.2 이력과 원본을 보존한다

- `IDENTITY`는 정정 뒤에도 같은 업무대상을 뜻하는 뿌리다.
- `PERIOD_FACT`는 적용기간을 가진 사실이다. 정정은 기존 사실을 침묵 변경하지
  않고 무효화·대체 관계와 새 사실 ID를 남긴다.
- `REVISION`은 실제 revision 구조가 승인된 영역에서만 사용한다.
- `CURRENT_PROJECTION`은 원장에서 계산한 현재값이며 임의 수정 가능한 별도
  진실원장이나 후속 이력의 정본 identity로 사용하지 않는다.
- 가져온 Excel 원본과 사용자가 수정한 값, 태그 보정의 적용 전·후 값을 구분해
  추적할 수 있어야 한다.
- 활성 기능에서 제외된 인정전환·옛 급여계획서 자료도 명시적인 퇴역·이관
  절차 전에는 삭제하지 않는다.

### 6.3 파생 결과는 다시 계산할 수 있어야 한다

- 자동카드, 태그 보정, 직원교체처럼 원천 수정으로 결과가 바뀌는 기능은 원천
  사실에서 결정적으로 다시 계산한다.
- 과거 결과를 조용히 덮어쓰거나 서로 다른 두 진실원장을 만들지 않는다.
- `Employee.role_current`, `Recipient.current_status` 같은 현재값 캐시는 기간
  이력의 투영이어야 한다.

### 6.4 미래 구조를 미리 만들지 않는다

- 현재 기능이 읽고 쓰지 않는 nullable FK, 상태, 범용 큐를 먼저 만들지 않는다.
- 미래 연결이 필요해질 때 해당 단계의 forward migration으로 추가한다.
- 코드목록값과 업무 코드는 원장 식별자로 취급하고 참조 중인 값을 변경·삭제하지
  않는다.
- 한 화면이나 trigger가 다른 단계의 업무카드·상태·실행행을 몰래 생성하지 않는다.

### 6.5 스키마·테스트·개인정보 안전

- DB 스키마는 Alembic migration으로만 변경하고 애플리케이션 시작 시
  `create_all()`을 사용하지 않는다.
- 테스트는 격리된 scratch DB 또는 롤백 가능한 트랜잭션에서 실행하며 운영
  원장을 오염시키지 않는다.
- 실제 이름·주민등록번호·연락처·계좌번호·PIN을 테스트·로그·문서 산출물에
  기록하지 않는다.
- 주민등록번호 원문 조회·정정은 일반 명단 수정과 분리된 강화 보안 규칙을 계속
  적용한다.

## 7. 고정 권한 방향

- 전체 일정, 수급자·직원 명단과 기본정보, 수급자·직원 완료현황, 사회복지사
  담당연결은 로그인 사용자 모두가 조회·변경할 수 있고 변경 로그를 남긴다.
- 사회복지사 방문일정은 해당 사회복지사와 센터장만 변경한다.
- 사회복지사 연차는 본인과 센터장이 조회하고 본인만 변경한다.
- 개인 할 일·개인 일정은 작성자 본인만 조회·변경하며 센터장도 볼 수 없다.
- 로그인 사용자 공통 기능에 별도의 사용자별 권한행이나 범용 권한 편집기를
  만들지 않는다.

## 8. 제외·보류 및 미결정

### 8.1 현재 상세 재설계에서 보류

- 본인부담금
- OCR
- 일반 입출력

메뉴는 유지하지만 이 문서에서 새 동작을 확정하지 않는다.

### 8.2 프로젝트 공통 제외

- 공단 청구자료 자동 제출과 공단 시스템 자동 업로드
- 외부 인터넷 또는 WorkCadence 연동
- 공유기 포트포워딩과 공인망 공개
- 모바일·태블릿 전용 구현·검증
- 반복일정/RRULE, 일정 자동추천, 지난달 일정 자동복사
- 다중센터 운영

방문요양과 방문목욕은 한 일정에 요양보호사 1명 또는 2명을 허용한다. 나머지
세 서비스의 제공인원 상한은 이번 재정렬에서 새로 확정하지 않는다.

### 8.3 결정 전 구현 금지

다음 네 항목은 자료 또는 사용자 결정이 있기 전까지 임의 확정하지 않는다.

1. 일정 중복과 재직·서비스 자격 불일치를 경고할지 차단할지
2. 기존 네 자동카드(`신규수급자`, `신규직원`, `퇴사직원`, `수급자종료`)를
   유지할지 보류할지
3. 실제 익명화 계획 Excel·태그 Excel의 열 이름, 식별자, 파싱 규칙
4. 잘못 연결된 센터장–직원 계정의 실제 사례와 재연결 절차

필요성이 생기면 기존 범위를 조용히 넓히지 않고 06 결정 현황 register에서
필요시점과 승인상태를 먼저 관리한다.

## 9. 정본 연결

영역별 정본의 정확한 목록과 판단순서는
[00 정본 문서 목록](00_정본_문서_목록.md)에만 둔다. 이 문서는 그 목록을
다시 만들지 않는다. 하위 정본이 이 문서의 새 방향과 충돌하면 충돌을 숨기지
않고 후속 S0 문서 정렬 대상으로 기록한다. 이 문서만 바뀌었다는 이유로 제품
코드나 DB를 자동 변경하지 않는다.

## 10. 최종 목표

> 현재 누가 관리 대상이고 무엇이 미완료인지, 계획일정과 실제 태그가 어디에서
> 다른지, 사회복지사가 무엇을 놓치기 쉬운지를 알려주되 공단이 이미 판단하는
> 일을 중복 구현하지 않는 사내망 전용 ERP를 구축한다.

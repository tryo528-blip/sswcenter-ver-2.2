# SSWCenter v2.2-alpha 개발로드맵·결정현황 v1.2

> 기준일: 2026-08-12 KST
> 지위: 최소기능 개발순서·착수/승격 gate·활성 결정 register의 단일 정본
> 비지위: 현재 branch·SHA·진행률·테스트 수치·작업자 배정의 원본이 아님

## 0. 사용법

- 이 문서는 무엇을 어떤 순서로 구현하고 언제 다음 단계로 넘길지만 정한다.
- 업무·UI·DB·보안 세부규칙은 `02~05`가 소유한다.
- 현재 SHA·실행명령·결과수치·작업자 보고는 활성 작업 패킷과 `review/` 증거가 소유한다.
- 옛 W1/W2/W3가 과거에 PASS였다는 사실은 새 최소계약의 PASS를 뜻하지 않는다.
- 과거 handoff·봉인·보고서는 역사 증거로 보존하고 최신 결정에 맞게 고쳐 쓰지 않는다.
- 제품 구현은 S0 정본·matrix 정렬 뒤에만 시작한다.

## 1. 개발 순서

정본 이후 제품 구현 순서는 다음으로 고정한다.

    S0  정본 00~06과 활성 테스트 matrix 재작성
    R0  인정전환·옛 W2·계약 projection 안전정리
    S1  계정관리·센터정보·센터 한마디·감사로그
    S2  기본정보·수급자 5개·직원 6개·자동카드 3개
    S3  사회복지사 담당·방문달력·마감·연차·개인일정
    S4  공단 계획일정 Excel·전체 일정·수동수정·변경로그
    S5  태그 Excel·자동보정·확인요망·직원교체·네 번째 카드
    S6  실제 탐색기형 파일함

각 slice는 자기 화면에 필요한 DB·API·UI·테스트만 소유한다. 다음 slice의 table·상태·nullable FK를 미리 만들지 않는다.

| 단계 | 현재 제품 기준 | 완료조건 |
|---|---|---|
| S0 | 정렬 중, 미봉인 | 00~06과 matrix의 옛 활성 정답 0건, 상호충돌 0건 |
| R0 | 미구현 | 기존 행 보존, 옛 UI/API/OpenAPI 제거, 새 forward migration, W2 앱 read-only |
| S1 | 기반만 있음 | 실제 설정 DB/API/UI, 권한·감사·세션무효화 통과 |
| S2 | 일부 기존 원장만 있음 | 확정 대상필터·완료/취소·원천투영 카드 3개 통과. 단 서류미비 대상 projection은 S4 일정 core 뒤 최종 봉인 |
| S3 | 실제 기능 없음 | 담당·월 1회 방문·3주 확대·연차·개인일정 권한 통과 |
| S4 | 달력 껍데기만 있음 | 실제 표본 parser, 전체 일정 CRUD·1/2인·감사 통과 |
| S5 | 실제 기능 없음 | 원본보존·날짜별 1회·30분 경계·직원교체 재판정 통과 |
| S6 | 가짜 파일 3개뿐 | 실제 CRUD·휴지통·복원·루트경계·원본 비연쇄삭제 통과 |

이 표는 2026-08-12 재정렬 기준선이다. 이후 진행률은 이 문서를 매 작업마다 고치는 대신 작업 패킷에서 보고한다.

## 2. 단계별 범위와 gate

### 2.1 S0 — 정본과 테스트 기준 정렬

범위:

- `docs/01~06`을 공단 복제 금지, 평가 완료, 일정, 사회복지사 업무흐름의 세 축으로 재작성한다.
- `docs/00_정본_문서_목록.md`은 01~06의 검수·해시가 끝난 뒤 마지막에 원자적으로 갱신한다.
- `review/WAVE1_CLEAN_TEST_MATRIX.md`와 활성 테스트 기대값을 새 최소계약으로 바꾼다.
- 옛 W2 급여계획서·WorkCadence 계획과 matrix는 `RETIRED — 역사 증거 전용`으로만 남긴다.
- S0에서는 제품 코드·DB·migration을 수정하지 않는다.

통과조건:

- 인정전환, 계약서명자·급여개시일, 상담상세, 건강검진 2원장, W2 hard guard, 4상태·단계카드, 확정월·옛 RFID가 활성 정답으로 남지 않는다.
- 기존 데이터 보존, 통보일 sole completion, 카드 중복원장 금지, 고정 권한이 01~06과 matrix에서 일치한다.
- 아직 남은 결정 2건과 입력 2건 외에 가짜 미결이 없다.

### 2.2 R0 — 안전폐기와 계약 최소화

범위:

- 인정전환 preview·최종확인·apply UI, API, OpenAPI, service 실행경로를 제거한다.
- 기존 인정·등급·계약·감사행은 보존한다.
- 적용된 `20260809_0018_w2_service_plan_notice.py`를 수정·downgrade하지 않는다.
- 새 forward migration으로 W2 전용 정방향 trigger 3개와 역방향 trigger 2개만 제거한다.
- 일반 `recipient_id_immutable` trigger는 유지한다.
- `recipient_service_plan_notice`는 기존 행·PK/FK·감사 연결을 보존하고 `erp_app` read-only로 만든다.
- 옛 계약연결 계산기를 활성 import·테스트에서 제거한다.

통과조건:

- 전후 W2 행 수·PK·전체 행 fingerprint가 같고 제거/유지 trigger와 권한이 정확하다.

### 2.3 S1 — 설정·계정·센터·감사

범위:

- 기존 `user_account`로 USER 생성, 기존 미연결 사회복지사·간호사 직원 1:1 연결, 닉네임, PIN 생성·재생성, 사용중지·해제를 제공한다.

통과조건:

- 일반 USER는 계정관리·감사로그 수정권한이 없다.

### 2.4 S2 — 기본정보·완료현황·자동카드 3개

범위:

- 수급자·직원 기본정보는 기존 원장을 연결하며 로그인 사용자 모두의 일반 수정과 감사를 허용한다. 민감정보 보안은 유지한다.
- 수급자 인정번호를 기존 인정 identity에서 표시한다.
- 수급자 `상담반영·반기평가·서류미비·인정만료·계약만료`와 직원 `보수교육·직원상담·인권교육·연간교육·건강검진·신규교육` 대상필터를 구현한다.
- 반기평가는 유효 통보일 입력만 완료이며 별도 완료값이 없다.
- 건강검진은 검진일만, 직원상담은 대상기간과 완료만 사용한다.
- 계약만료·인정만료·반기평가 카드를 원천자료에서 계산한다.
- 카드 전용 범용 원장·단계·담당자·첨부·복제 완료값을 만들지 않는다.
- 서류미비 완료원장·완료 mutation은 S2에서 준비한다. 대상자 projection은 S4
  `service_schedule` core 뒤에 연결하며 사회복지사 달력자료로 대신하지 않는다.

통과조건:

- 수급자 5개·직원 6개 기간경계와 완료·완료취소가 mutation-sensitive하게 통과한다.
- 완료 UI checkbox가 없고 반기평가 통보일·건강검진 검진일 예외가 정확하다.
- 통보일이 없으면 임의 날짜 없이 미완료이고, cap·D-100·D-45·overdue가 원천 정정 뒤 다시 계산된다.
- 별도 permission 부여행 없는 USER도 명단·기본정보·완료현황을 공동 사용하고 변경감사가 남는다.
- S2의 다른 항목은 독립 검수할 수 있지만 S2 전체 봉인은 S4 일정 core와 서류미비
  대상 projection 수용검사까지 끝난 뒤다.

### 2.5 S3 — 사회복지사 업무 허브

범위:

- 사회복지사를 선택하면 담당 수급자와 방문일정을 모든 로그인 사용자가 본다.
- 담당 연결은 로그인 사용자 모두가 관리·감사한다.
- 방문일정은 해당 사회복지사와 ADMIN만 변경하고 사회복지사+수급자+달력월당 최대 1건이다.
- 월간 달력은 작업영역을 채우고 날짜 클릭 시 전주·이번주·다음주 3주 확대, 우클릭 시 같은 사람·달의 월간으로 복귀한다.
- 자동마감은 실제 기한일에 표시하지만 달력에서 직접 완료하지 않는다.
- 연차는 본인과 ADMIN 조회·본인 수정, 개인 할 일·일정은 본인만 조회·수정한다.

통과조건:

- 권한을 API 응답과 mutation 모두에서 검사한다.
- 개인 항목은 다른 계정·ADMIN 응답과 감사로그에서 사건·내용이 모두 없다.
- 방문일정에 수급자 상세링크가 없고 달력 완료값을 복제하지 않는다.

### 2.6 S4 — 전체 일정과 계획 Excel

범위:

- 5개 서비스의 수급자·서비스·요양보호사·날짜·시작·종료 일정을 만든다.
- 로그인 사용자 모두가 조회·생성·수정·삭제·Excel 가져오기를 하고 감사한다.
- 방문요양·방문목욕은 1명 또는 2명 제공자를 허용한다.
- 일시대체는 요양보호사 일반 수정이며 직원교체 업무를 직접 만들지 않는다.
- 계약·인정·`care_assignment`를 일정의 필수 FK·저장 gate로 쓰지 않는다.
- 실제 가명 계획 Excel 표본 전에는 parser header·식별키를 발명하지 않는다.
- `service_schedule` core와 수동 CRUD가 생기면 S2 서류미비 대상 projection을
  연결한다. 이 연결에는 실제 Excel parser 표본이 필요하지 않다.

통과조건:

- 실제 표본의 정상·오류·중복행 parser가 통과한다.
- 일정과 2인 제공자 변경이 한 transaction과 감사로 남는다.
- 수급자–요양보호사 일정이 있는 수급자×월만 서류미비 대상이고 사회복지사
  방문·연차·개인일정은 대상에 섞이지 않는다.
- 활성 register의 일정 저장판정이 결정되기 전에는 해당 제약을 임의로 고정하지 않는다.

### 2.7 S5 — 태그 보정·직원교체·네 번째 카드

범위:

- 원본 bytes·SHA-256·원본행·자동수정 전후값을 불변 보존한다.
- 수급자·요양보호사·날짜와 시작 범위를 통과한 후보가 정확히 1개일 때만 보정한다.
- `P-59~-30 → P-30`, `P-29~P+29 → P`, `P+30~+59 → P+30`을 적용하고 정확한 ±60은 `확인요망`이다.
- 서비스시간은 태그 종료-시작을 30분 단위로 내리고 30~480분으로 처리해 보정 시작에 더한다.
- 종료태그 없음, 계획만, 태그만, 범위초과, 비정상, 후보 0/2개 이상은 수정 없이 `확인요망`만 표시한다.
- 적용완료 날짜는 이후 파일에서 건너뛰고 새 날짜만 처리한다.
- 실제 제공자 묶음의 집합차이로 직원교체를 만들고 첫 제공일+13일·하루대체·Day14 예외·원천정정 재판정을 적용한다.

통과조건:

- 후보 0/1/2, ±60, 30/480, 원자수정, 날짜별 1회가 실제 PostgreSQL에서 통과한다.
- 2인 `A+B→A+C`는 C만 대상이고 첫 제공·빠진 사람·순서변경은 새 case가 아니다.
- 상담내용·사유 없이 대상·완료만 남고 직원교체 카드가 원천 case에서 계산된다.

### 2.8 S6 — 실제 파일함

범위:

- 탐색기형 폴더 생성·이동·이름변경·업로드·다운로드·휴지통·복원을 만든다.
- 일반 파일함은 로그인 사용자 모두 공동 사용하고 모든 변경을 감사한다.
- 영구삭제·버전관리·자동보존기간·GC는 만들지 않는다.
- 감사·시스템·가져오기 로그와 Excel 원본은 일반 파일함에서 분리한다.

통과조건:

- 실제 파일 bytes와 DB metadata의 생성·이동·복원·감사가 일치한다.
- 절대경로·상위경로·symlink·junction·reparse point의 루트 탈출이 실패한다.
- 일반 파일 휴지통 이동이 import 원본·감사·시스템로그를 연쇄삭제하지 않는다.
- 영구삭제 API가 없다.

## 3. 공통 검증·승격 gate

각 slice는 고정 후보 SHA의 별도 clean 검수환경에서 다음을 통과한다.

- 현재 DB forward upgrade와 fresh install migration chain
- PostgreSQL catalog·FK·CHECK·trigger·권한·동시성
- backend 단위·통합·PostgreSQL 회귀와 lint/type check
- OpenAPI와 frontend client drift 없음
- frontend unit·lint·build와 실제 브라우저 E2E
- 권한·CSRF·민감정보·row_version·감사 회귀
- 변경 slice의 기존 데이터·원본 보존과 rollback/restore 증거
- 해당 slice 밖 미래구조와 구현금지 항목 부재

결과는 `PASS`, `FAIL`, `BLOCKED`다. 폐기 기능의 기존 테스트 PASS는 새 계약의 PASS 증거가 아니다. 테스트 때문에 폐기 기능을 되살리지 않고 정본과 matrix를 먼저 고친다.

| ID | 종류 | 항목 | 막는 범위 |
|---|---|---|---|
| D-01 | USER_DECISION_REQUIRED | 동일 요양보호사의 서로 다른 일정 겹침, 동일 수급자의 서로 다른 일정 겹침, 근무일 재직·서비스자격 불일치를 각각 경고 후 허용할지 저장차단할지 | S4 저장판정 |
| D-02 | USER_DECISION_REQUIRED | `신규수급자·신규직원·퇴사직원·수급자종료` 네 옛 자동카드를 각각 유지할지 보류할지 | 해당 추가 카드만 |
| I-01 | SAMPLE_REQUIRED | 실제 공단 계획일정·태그 Excel의 가명 표본과 sheet·header·식별값 | S4/S5 parser |
| I-02 | CASE_REQUIRED | 기존 ADMIN 직원연결이 실제로 잘못된 사례와 승인된 재연결 절차 | 예외 재연결만 |

D-01에서 정상 2인 급여는 충돌이 아니며 계약·인정·`care_assignment`는 어느 선택에서도 필수검사가 아니다. I-01 전에는 이름만으로 사람을 추측하거나 여러 후보 중 최근접을 고르는 parser를 만들지 않는다. I-02 전에는 일반 재연결 기능을 만들지 않는다.

이 4건은 해당 부분만 막는다. S0·R0·S1, S2 확정부분, S3, S6과 S4/S5의 독립된 확정부분까지 임의로 막지 않는다.

## 5. DEFER와 범위 밖

- 본인부담금·OCR·일반 입출력은 `DEFER`다. 기존 메뉴·자료를 삭제하지 않으며 이번 로드맵에서 상세 설계·구현하지 않는다.
- 외부 WorkCadence 연동은 없다.
- 일반화 queue·lease·heartbeat·자동수집 플랫폼, 임의 권한편집기, 직원합치기, 외부 자동발송은 필요성이 별도 확정되기 전까지 만들지 않는다.
- 파일함 S6는 OCR과 독립된 필수기능이다.
- 백업·복원·보안 기반은 유지하지만 새 사용자 기능처럼 범위를 키우지 않는다.

## 6. 승격 원칙

- exact 후보 SHA와 검증결과가 일치해야 한다.
- review-only 문서 변경과 제품 implementation 변경을 구분한다.
- 실패·미검증 후보를 정본 PASS·보호 branch·release로 승격하지 않는다.
- 과거 branch를 일반 merge하여 인정전환·옛 W2·상담상세·확정월 등을 되살리지 않는다.
- 실제 ref 조작·tag·push는 선행 gate PASS와 사용자 승인 범위 안에서만 수행한다.
